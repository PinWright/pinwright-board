# BPIR `bind_dispatcher` on external target + local `event:@Handler` produces stale CreateDelegate

The BPIR pattern `bind_dispatcher DispatcherName(Target: %externalObj, event: @LocalCustomEvent)` — i.e., bind a local class's custom event as a listener on an external object's dispatcher — produces a `UK2Node_CreateDelegate` whose `MemberReference.MemberParent` is set to the wrong class. On the post-P0-2 integrity gate this is detected and the transaction is rolled back with `INTEGRITY_FAILURE: BPIR compile produced a blueprint with 1 stale reference(s)`.

## Repro (observed this session, `W_AppReplayEditor`)

Root widget's Construct-event handler spawns an overlay widget via `CreateWidget`, casts it, adds to viewport, then needs to bind the overlay's `OnCommitted` dispatcher to a local custom event `OnPlacementCommitted`:

```
entry custom_event ShowManualPlacement(enum<EReplayManualPlacementTarget> InTarget, struct<FTransform> InTransform) {
    %player = call GetOwningPlayer(Target: self)
    %overlay = call CreateWidget(OwningPlayer: %player, Class: /App/.../W_ReplayEditor_ManualPlacementOverlay_C)
    %typed = cast<W_ReplayEditor_ManualPlacementOverlay_C>(%overlay) [success -> @ok, fail -> @done]
@ok:
    call AddToViewport(Target: %typed, ZOrder: 1000)
    bind_dispatcher OnCommitted(Target: %typed, event: @OnPlacementCommitted)   # <-- problem line
    call Begin(Target: %typed, InTarget: $InTarget, InitialTransform: $InTransform)
@done:
}

entry custom_event OnPlacementCommitted(enum<EReplayManualPlacementTarget> CommittedTarget, struct<FTransform> NewTransform) {
    call ApplyManualPlacementResult(Target: $CommittedTarget, NewTransform: $NewTransform)
}
```

Result: `INTEGRITY_FAILURE: BPIR compile produced a blueprint with 1 stale reference(s) — transaction rolled back.`

Remove only the `bind_dispatcher OnCommitted(...)` line → compiles cleanly. So the failure is narrowly this one instruction.

## Likely root cause

`bind_dispatcher` with an external `Target:` emits a `UK2Node_AddDelegate` on the target object's dispatcher. The upstream `UK2Node_CreateDelegate` that feeds the `AddDelegate`'s `Delegate` pin is expected to carry:

- `SelectedFunctionName` = the local custom event's UFunction name (correct; emitted this way).
- `MemberReference.MemberParent` = **self's generated class** (W_AppReplayEditor_C) — because the custom event lives on `self`, not on the target class.

BPIR appears to be setting `MemberReference.MemberParent` to the **target's class** (the overlay's `UReplayEditorManualPlacementWidget` / `W_ReplayEditor_ManualPlacementOverlay_C`) by following the dispatcher-owner class rather than the `event:@Handler`'s owning class. The name resolves on self but not on the target class, so the CreateDelegate is effectively stale — `IsValid(bDontUseSkeletalClassForSelf=true)` on the gate's check fails because it scopes to `MemberParent` (the target class).

The in-editor hand-authored equivalent of this pattern emits a CreateDelegate with `DelegateOwnerClass` set to the self-class; manual testing in UE5's Blueprint editor confirms the connection is valid at runtime.

## Why the integrity gate flags it

Per `B-bp-saved-state-corruption-mcp-edits` P0-2, `ValidateBlueprintGraphIntegrity` calls `UK2Node_CreateDelegate::IsValid(&msg, /*bDontUseSkeletalClassForSelf=*/true)`. That method resolves `SelectedFunctionName` against the node's `DelegateOwnerClass` (which BPIR sets from `MemberReference.MemberParent`). With MemberParent wrong, the lookup misses, the node is marked invalid, and the gate rolls back the transaction. The gate is working as designed — BPIR is the one producing bad data.

## Impact

Any BPIR that wires an external object's delegate to a local custom event cannot currently save. This is a common pattern:
- Editor widget spawns child widget, binds its `OnChanged` to a local handler.
- World subsystem delegate wiring from a widget BP.
- Cross-widget communication in multi-window UI.

Forces either:
1. Rewriting the flow to avoid cross-object delegate binding (e.g. routing the callback through a C++ method on the target that holds a pointer back to self).
2. Manually editing the emitted BP graph in the UE editor after BPIR to fix the CreateDelegate's `DelegateOwnerClass`.

## Workaround (adopted this session)

Give the overlay widget a C++ pointer field `TWeakObjectPtr<UAppReplayEditorWidget> OwningEditor` set at `Begin(...)` time, and have `StopOverlay` call `OwningEditor->ApplyManualPlacementResult(...)` directly instead of broadcasting `OnCommitted`. The BP side drops the `bind_dispatcher` and the `OnPlacementCommitted` custom event entirely. Requires a C++ change; not a BPIR-only workaround.

## Proposal

In the BPIR emitter's `bind_dispatcher` handler: when the `event:@Handler` refers to a custom event declared in the same compile unit OR on the caller's class, set the emitted `UK2Node_CreateDelegate`'s `MemberReference.MemberParent` (and `DelegateOwnerClass`) to **self's generated class**, not the target object's class. The target class still drives the `AddDelegate` node (because that's where the multicast dispatcher lives), but the delegate *signature/owner* resolution must scope to the event's defining class.

Concretely:
1. Resolve `@Handler` against `Context.SelfClass` first.
2. If found, set `CreateDelegateNode->SelectedFunctionName = <name>` and `CreateDelegateNode->DelegateReference.SetExternalMember(<name>, Context.SelfClass)`.
3. Only fall back to target-class resolution when `@Handler` does NOT exist on self.

- `#5-signature-mismatch-reason` `OPEN` tester — Precise failure reason now available from the latest-round `blueprint.compile saveAfterCompile: true` response's `integrityFailures` array. The exact `reason` string: `"K2Node_CreateDelegate SelectedFunctionName='OnOpenReplayRequested_Event' fails generated-class resolve: Function/event 'OnOpenReplayRequested_Event' does not match the necessary signature."` — this is a **signature mismatch** error, not name-not-found, not GUID mismatch. `UK2Node_CreateDelegate::IsValid` calls `DelegateReference.ResolveMember<UFunction>(GetScopeClass())` which succeeds by name, then checks parameter compatibility via `IsSignatureCompatibleWithScriptDelegate` and fails. C++ dispatcher: `DECLARE_DYNAMIC_MULTICAST_DELEGATE_OneParam(FOnOpenReplayRequested, const FEditorReplay&, Replay)` — one param, `const FEditorReplay&`. BPIR-emitted custom event signature `entry custom_event OnOpenReplayRequested_Event(struct<EditorReplay> Replay)` resolves to a BY-VALUE `FEditorReplay` parameter (confirmed by the gate's `IsSignatureCompatibleWithScriptDelegate` rejecting it). The `&` suffix form `struct<EditorReplay>& Replay` parses (BPIR accepts the syntax, UE compile reports UpToDate) but the gate STILL rejects with the same signature-mismatch reason — either `&` alone is not equivalent to `const&` for signature-compat purposes, OR BPIR's parser accepts `&` but does not set `CPF_ReferenceParm` on the emitted `FProperty`. Need: (a) BPIR syntax for `const FStruct&` on custom-event params that actually sets both `CPF_ConstParm | CPF_ReferenceParm` flags on the emitted parameter property; (b) if such syntax doesn't exist, add one — this is required to author ANY custom_event listener for a `DYNAMIC_MULTICAST_DELEGATE_*Param` on a non-primitive type, which is the overwhelming majority of engine-defined delegates. Trying `(const struct<EditorReplay>& Replay)` produces `COMPILE_FAILED: Could not resolve value '$Replay' for pin 'Replay'` — the `const` keyword isn't recognized as a param-modifier. - `#6-const-ref-param-fix` `IN-REVIEW` developer — Landed the BPIR parser fix for `const struct<T>& Name` param syntax. Root cause (confirmed by tester's "signature mismatch" reason string and verified in engine): the BPIR type parser `FCodePinResolver::ConvertCppTypeToPinType` didn't recognize `const` prefix or `&` suffix, so a custom_event param like `(const struct<EditorReplay>& Replay)` either failed parse entirely (→ `COMPILE_FAILED: Could not resolve value '$Replay' for pin 'Replay'`) or parsed by-value (→ `UFunction` param emitted with only `CPF_Parm`, missing `CPF_ReferenceParm | CPF_ConstParm`). The pre-save gate's `IsSignatureCompatibleWithScriptDelegate` check then rejected the binding because `DECLARE_DYNAMIC_MULTICAST_DELEGATE_OneParam(..., const FStruct&, Name)` dispatchers require a matching const-ref parameter. Fix at `Source/EditorAutomationRpcGateway/Private/Compiler/CodePinResolver.cpp:271-311`: `ConvertCppTypeToPinType` now strips a leading `const ` (case-insensitive) and sets `FEdGraphPinType::bIsConst = true`, then strips a trailing `&` and sets `FEdGraphPinType::bIsReference = true`, BEFORE the inner type-kind matchers run (so `struct<T>` / `object<T>` / `array<T>` detection still succeeds on the stripped remainder). UE's BP compiler maps these pin-type bits to `CPF_ConstParm | CPF_ReferenceParm` on the emitted parameter property at skel/gen compile time. Accepted shapes now include: `const struct<T>& Name`, `struct<T>& Name` (reference-only, rare but valid), `const struct<T> Name` (const-by-value). Regression test: `EditorAutomationRpcGatewayTests/Private/Bpir/TestBpirConstRefParam.cpp` (`FBpirConstRefStructParamEmitsCorrectFlagsTest`, path `EditorAutomationRpcGateway.Bpir.Compiler.Integration.CustomEventConstRefStructParamEmitsCorrectFlags`) — compiles `entry custom_event HandleVec(const struct<Vector>& V) {}` on a transient AActor-based BP using engine-provided `FVector` struct (no project dependencies), runs `FKismetEditorUtilities::CompileBlueprint`, then looks up `HandleVec` on `GeneratedClass` and inspects the `V` parameter's `FStructProperty`.
