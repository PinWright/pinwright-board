# `widget_event` BndEvt binding invalid for XML-imported CommonButton-derived widgets

`entry widget_event <WidgetVar>.OnClicked() { ... }` (or `.CommonButtonBaseClicked()`) fails to bind the delegate when the widget variable was added via `widget_import_xml` into an existing Blueprint that already has other `CommonButtonBaseClicked` bindings on sibling buttons.

**Repro:**
1. Take an existing widget BP (`W_SingleRaceResultsFrame`) that has `CloseRaceResults` and `ShowLeaderboardOnRace` as `W_ImageButton_C` variables with `CommonButtonBaseClicked` delegate bindings wired normally.
2. Use `widget_import_xml` (add mode) to add a new `<W_ImageButton_C name="SaveButton" ...>` child.
3. Run `compile_bpir` with `entry widget_event SaveButton.OnClicked() { ... }` — reports `success: true`, 6 nodes, but with warning "OnClicked (SaveButton) does not have a valid matching component!".
4. `widget_bind_event` on the same widget returns `isDelegateValid: false, customFunctionName: "None"`.
5. Decompile shows the entry as `entry event None()` with warning "delegate binding is invalid — the delegate may no longer exist on the component class".
6. Retry with `.CommonButtonBaseClicked()` instead of `.OnClicked()` — same result, plus `mode: replace` does NOT remove the first broken entry, leaving two invalid BndEvt nodes.

**Expected:** BndEvt node properly bound to SaveButton's inherited click delegate (same as existing CloseRaceResults binding).

**Observed:** Node created but delegate property points to nothing (`None`). BP compiles with warning. Runtime click does nothing.

**Counter-example (works):** Same BPIR code (`entry widget_event SaveButton.OnClicked() { ... }`) on `W_HUD_RaceTrackEnd` with a freshly-XML-imported `W_ImageButtonWithBlurBG_C` named `SaveButton` produces a valid binding: `isDelegateValid: true, customFunctionName: "BndEvt__W_HUD_RaceTrackEnd_SaveButton_K2Node_ComponentBoundEvent_4_OnClicked__DelegateSignature"`. The difference appears to be related to the parent BP's pre-existing delegate bindings on sibling buttons of the same inheritance tree.

**Hypothesis:** BPIR compiler's delegate lookup on an XML-imported widget doesn't properly resolve the inherited MulticastDelegate property when the BP's class is mid-recompile or the widget-variable-to-delegate index wasn't refreshed after the XML import. A post-import `blueprint_compile` didn't fix it.

**Workaround:** Manual Details-panel binding in the BP editor.

**Context:** Found while implementing replay subtask 02's cross-widget Save buttons. The HUD binding works; the 3 results modals all fail identically.

Also discovered `mode: replace` did not remove a previous broken `OnClicked` binding when retrying with `CommonButtonBaseClicked` — accumulated two invalid entries.
- `#2-skeleton-class-preferred` `IN-REVIEW` developer — Fixed `CodeNodeEmitter::CreateComponentEventNode` (lines 836-859) to prefer `SkeletonGeneratedClass` over `GeneratedClass` for the widget-variable `FObjectProperty` lookup. Root cause: `widget_import_xml`'s `MarkBlueprintAsStructurallyModified` regenerates only the skeleton, leaving `GeneratedClass` stale. When a BP already had sibling bindings, the previously-compiled `GeneratedClass` didn't contain the newly XML-imported widget's property, so `FindPropertyByName` returned null, `InitializeComponentBoundEventParams` fell through its failure branch, and the BndEvt got `DelegateOwnerClass=BP->GeneratedClass` (wrong). Skeleton-first lookup finds the property (always fresh post-`MarkBlueprintAsStructurallyModified`), and the `DelegateOwnerClass` fallback assignments (lines 880/890) now use the resolved `BPClass` rather than `BP->GeneratedClass` directly. Fresh-BP path still works because skeleton equals generated in that case.
