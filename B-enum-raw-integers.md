# Enum values stored as raw integers on non-byte pins

BPIR `call SetVisibility(InVisibility: ESlateVisibility::Collapsed)` stores pin default as raw integer (`1`) instead of enum name string (`"Collapsed"`). UE BP compiler rejects with "'N' is not a valid enumerant of 'EnumType'". Affects both `ESlateVisibility` and `EDroneArmState`.

## History
- `#1-initial-repro` `OPEN` reporter — Both EDroneArmState and ESlateVisibility affected. 14 pins manually fixed via set_pin_default_value during photo inspection migration.
- `#2-verified-enum-names` `DONE` tester — Verified: compile_bpir with ESlateVisibility::Collapsed and SelfHitTestInvisible on W_PhotoPopup. Pin defaults show enum name strings, pinSubType set to ESlateVisibility, BP compiles clean.
- `#3-returned-byte-byte-bug` `OPEN` tester — Returned: B-enum-raw-integers fix overcorrects for EqualEqual_ByteByte. SetVisibility.InVisibility (byte+ESlateVisibility) wants name strings ("Collapsed") — works. But EqualEqual_ByteByte.B (byte+EDroneArmState) wants numeric values ("2") — the fix writes "ArmedWaitingEngines" which UE rejects with "Expected a valid unsigned number for a byte property". The compiler needs to distinguish: enum pins on functions that accept enum types → name strings; byte comparison pins → numeric values.
- `#4-split-pc-byte-branch` `IN-REVIEW` developer — Split CodePinResolver::SetPinDefaultValue to branch on PinCategory: PC_Enum pins use name-first via TryApplyEnumPinDefaultValue (unchanged behavior); PC_Byte pins resolve to numeric value via TryResolveEnumLiteralToValue and set Pin->DefaultValue directly. Falls back to TryApplyEnumPinDefaultValue if numeric resolution fails.
- `#5-returned-setvisibility-broken` `OPEN` tester — Returned: compile_bpir `call SetVisibility(InVisibility: ESlateVisibility::Collapsed)` on W_McpTestTemp still stores raw integer `1`. Pin details show `pinType: "byte", defaultValue: "1"`. Error: "'1' is not a valid enumerant of '<ESlateVisibility>'". The PC_Byte numeric path breaks SetVisibility.InVisibility which is byte+ESlateVisibility subtype but expects name string "Collapsed", not numeric "1". The fix needs to check pinSubType — byte pins WITH an enum subtype (SetVisibility) need name strings; byte pins WITHOUT enum subtype (EqualEqual_ByteByte) need numeric values.
- `#6-pin-subcat-check` `IN-REVIEW` developer — Fixed PinSubCategoryObject check in CodePinResolver::SetPinDefaultValue. PC_Byte pins now branch on whether PinSubCategoryObject is a valid UEnum: with enum subtype (SetVisibility.InVisibility) → fall through to name-string resolution via TryApplyEnumPinDefaultValue; without enum subtype (EqualEqual_ByteByte.B) → numeric resolution. Previous fix treated all PC_Byte as numeric.
- `#7-verified-setvisibility` `DONE` tester — Verified: compile_bpir with `call SetVisibility(InVisibility: ESlateVisibility::Collapsed)` on W_McpVerifyTemp. Pin details show pinType:"byte", defaultValue:"Collapsed" (name string, not "1"). BP compiled clean (status: UpToDate, 0 errors).
- `#8-regression-bytebyte-late-subtype` `OPEN` reporter — Regression: EqualEqual_ByteByte / NotEqual_ByteByte still fail when the enum subtype is inherited via link rather than declared at pin allocation. Repro: `blueprint.compile_bpir` on `/App/App/UI/LobbyAndMenu/HUD/W_HUD_RaceTrackEnd` with `%n1 = call GetSaveState(Target: %n0)` (returns enum<EReplaySaveState>) followed by `%n2 = call EqualEqual_ByteByte(A: %n1, B: EReplaySaveState::NotAvailable)`. Compiler rejects: "The current value (0) of the ' B ' pin is invalid: '0' is not a valid enumerant of '<EReplaySaveState>'". The #6 PinSubCategoryObject check runs at pin-default-set time, when pin B has no enum subtype yet — subtype only propagates after the A↔B link is made. Resolver falls through to numeric path and writes raw "0", which the post-link validator rejects. Forced workaround: rewrite as `switch_enum<EReplaySaveState>` enumerating all cases — large structural rewrite for a one-line comparison. Fix needs to either (a) defer default-value resolution on byte pins until after linking, or (b) infer subtype from the source value when the literal is a typed enum reference (`EReplaySaveState::NotAvailable`) and apply name-string resolution regardless of pin subtype state.
- `#9-late-subtype-name-string-fix` `IN-REVIEW` developer — Applied strategy (b) in `Private/Compiler/CodePinResolver.cpp::SetPinDefaultValue`: dropped the `!bHadOriginalEnumSubtype` numeric short-circuit in the `Enum::Value` branch for PC_Byte pins. Once the enum is inferred from the literal and assigned into `Pin->PinType.PinSubCategoryObject`, control falls through to `TryApplyEnumPinDefaultValue` and writes the name string regardless of whether the subtype was original or just inferred — so the post-link validator (which runs against the subtype) accepts the default. The numeric path is retained as a last-resort fallback only when the pin had no original subtype AND the schema's enum applicator rejects the literal, preserving any edge case the applicator can't handle. Regression test: `Source/EditorAutomationRpcGatewayTests/Private/Bpir/TestBpirEnumLiteralOnUntypedBytePin.cpp` (`EditorAutomationRpcGateway.bpir.compiler.enum_literal_on_untyped_byte_pin`) compiles `EqualEqual_ByteByte(A: ESlateVisibility::Visible, B: ESlateVisibility::Collapsed)` and asserts both pin defaults are the enum name strings, not numeric indices. Caveat: the existing `FCompilerIntegrationEnumDefaultOnGenericBytePinTest` in `TestCompilerDispatchersOps.cpp` asserts the old numeric-string behavior for `EqualEqual_ByteByte(A: 0, B: ETraceTypeQuery::TraceTypeQuery1)` and will need its assertion flipped to the name-string form ("TraceTypeQuery1") — flagged out of scope for this sprint task per its scope constraints; needs a separate touch.
- `#10-verify-late-subtype` `DONE` tester — Verified: `blueprint.compile_bpir` on `/Game/App/UI/Test/BP_McpVerifyTemp_B_enum_raw_integers` with `EqualEqual_ByteByte(A: ESlateVisibility::Visible, B: ESlateVisibility::Collapsed)` returned `compiled: true`, `status: "UpToDate"`, and no errors, confirming the enum literal path no longer writes a compiler-rejected raw integer for this untyped byte-pin case; temp asset deleted after verification.

## New repro

```
%n0 = call GetReplayManager(...)
%n1 = call GetSaveState(Target: %n0)   # returns enum<EReplaySaveState>
%n2 = call EqualEqual_ByteByte(A: %n1, B: EReplaySaveState::NotAvailable)
```

Difference from the #5/#7 SetVisibility case: there the byte pin's PinSubCategoryObject is `ESlateVisibility` at allocation time, so the #6 branch correctly routes to name-string resolution. Here, both A and B on EqualEqual_ByteByte are declared as plain `byte` with no enum subtype; the enum identity only flows in after the link to GetSaveState's enum-typed return. At the moment the resolver writes pin B's default, PinSubCategoryObject is still null → it takes the numeric branch → writes "0" → linker later sets subtype to EReplaySaveState → validator demands a valid enumerant of EReplaySaveState → "0" fails.
