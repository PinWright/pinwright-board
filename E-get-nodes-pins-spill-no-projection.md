# `blueprint.graph.get_nodes` always emits full pins+adjacency, so even a small graph spills

`blueprint.graph.get_nodes` is the canonical first call in every BP-graph
workflow: enumerate the graph's nodes so you can pick one to inspect/edit. But
the handler unconditionally emits, **for every node**, the complete `pins`
array — and each pin carries its full `linkedTo` adjacency list (one
`{nodeId, pinName}` per connection) — on top of `nodeId`/`nodeName`/`nodeType`/
`nodeTitle`/`comment`/`x`/`y`
(`Source/PinWright/Private/Handlers/Blueprint/BlueprintGraphInspectionHandler.cpp:391-428`).

There is **no narrowing lever**: the registered params are only `graphName`,
`includePinDefaults`, `includeNodeState` (`:377-382`) — all of which *add* to
the payload; none of them reduce it. Unlike its sibling `get_execution_flow` in
the same file, which already takes `offset`/`pageSize`
(`:1219`, `:1247-1257`, `ApplyChainPagination` `:1473`), `get_nodes` has **no
`limit`/`offset` pagination, no `fields` projection, and no `namesOnly` mode**.
So the response size scales with (nodes × pins × connections) and the caller
cannot ask for the lightweight "ids+titles so I can pick" shape the enumerate
intent actually needs.

The practical effect: an **8-node** EventGraph (a tiny graph) already crosses
the 10000-char inline budget, returns `outputTooLong`, and the full payload is
written to `Saved/EditorAutomation/HttpResponses/.../<uuid>.json`
(`E-http-response-spill`, DONE) — forcing the caller to `Read` the spilled file
just to see the node list and pick one. The spill mechanism worked as designed;
the friction is that the *only* method whose job is "list the nodes" has no way
to stay inline, so the spill fires on graphs far smaller than anyone would
expect.

## What it should do

Give `get_nodes` a narrowing lever so the common "enumerate to pick" call stays
inline, mirroring levers that already ship elsewhere in this family:

- A `fields` projection (or a `namesOnly`/`summary` boolean) that returns just
  `nodeId`/`nodeName`/`nodeType`/`nodeTitle`/`x`/`y` and **omits the heavy
  `pins`/`linkedTo` arrays** unless explicitly requested. The pin adjacency is
  already available in full via `get_graph_connections` and per-node via
  `get_node_details`/`get_node_details_batch`, so it does not need to be forced
  into every enumerate call.
- And/or `limit`/`offset` pagination plus a `totalCount` readback (the same
  `offset`/`pageSize` shape `get_execution_flow` already implements at
  `:1219`/`:1473`), so a large graph can be walked a page at a time.

Either keeps the textbook list call inline; the verbose full-fidelity shape
stays available opt-in for callers that want it.

## Distinct from

- `E-get-nodes-no-count-field` (OPEN) — same method, but that ticket is the
  missing `nodeCount` summary field; this ticket is that the *body* is
  unconditionally heavy and unnarrowable. Orthogonal (a count field does not
  shrink the payload).
- `E-node-comment-field-name-drift` (OPEN, judge-filed for this same task) —
  the `comment`/`nodeComment` key divergence; a naming issue, not size.
- `E-asset-list-pagination-undocumented-spills` (OPEN) — that reader **already
  has** a `pagination.limit` lever and only needs docs; `get_nodes` has **no
  lever at all**, so this is a code fix (add the lever), not a docs fix.
- The `*-no-limit-spills` family (`E-actor-list-no-limit-spills`,
  `E-inspect-list-objects-no-limit-spills`, `E-skeleton-list-bones-no-limit-spills`,
  etc.) — same shape of fix (add `limit`+projection to a verbose reader) but on
  different methods; none names `blueprint.graph.get_nodes`.
- `E-get-node-details-batch-undiscovered-on-read-path` (OPEN) — discoverability
  of the *detail* verb, a different method on the drill-in step.

## Evidence

From the struggle audit of a clean BP event-graph tidy-up task (focus
`blueprint.graph.set_node_property`, namespace `blueprint.graph`, outcome
**ergo** — all 14 calls `ok`/non-error; every write round-tripped on the first
try). The friction note, verbatim: *"get_nodes output exceeded the 10k display
limit and was written to disk (read from file)"*. The call log shows
`blueprint.graph.get_nodes {graphName:"EventGraph", includeNodeState}` on
`/Game/ExampleContent/Blueprint_Communication/Blueprints/BP_Light_Bulb_Basic`
returning **8 nodes (paged to disk)** — an 8-node graph already overflowing the
inline budget because each node dragged its full `pins`+`linkedTo` payload, with
no projection available to trim it.

Severity Medium: by the rubric a response-spill that only forces a Read is Low,
bumped up one level because `get_nodes` is an every-session method on the hot
BP-graph read path (the first call of essentially every graph workflow), so the
spill recurs constantly.
