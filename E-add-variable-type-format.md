# `blueprint.add_variable` rejects the full-path / `class:`/`struct:` variableType forms it advertises

> **Live concern (`#5`):** this is now a hard functional bug, not just an ergonomic gap. The handler's own `TYPE_NOT_FOUND` error message advertises `full paths (/Script/Module.Type or /Game/Path/BP_Asset)` and the `variableType` param description advertises `'class:/Script/X.Y'` / `'struct:/Game/...'`, yet every `/`-leading (and `class:`/`struct:`-prefixed `/`-leading) form is categorically rejected with `TYPE_NOT_FOUND`. Short names (`DamageType`) and wrappers (`object<UDamageType>`) resolve fine — only the advertised path forms fail. (`category` stays `ergonomic` because the board derives it from the `E-` id prefix; severity is raised to High to reflect the advertised-but-rejected contract.)
>
> The original report (below) covered the broader format-consistency story; the `#2`/`#3` unification fix landed for short names, but the full-path forms regressed silently with no covering test. See `#5-regression-full-path-rejected` for the live repro and root cause.

`blueprint.add_variable`'s `variableType` parameter doesn't document which formats are accepted, and different forms produce different results silently.

**This session's results:**

| Input | Result |
|-------|--------|
| `FEditorReplay` | `TYPE_NOT_FOUND: Could not resolve variableType 'FEditorReplay'` |
| `struct:EditorReplay` | `TYPE_NOT_FOUND` |
| `class:MyReplaySelectWidget` | `TYPE_NOT_FOUND` |
| `UMyReplaySelectWidget*` | **Succeeds** but variable is stored with `type: "object"` (no subtype), breaking downstream BPIR method resolution on that variable |
| `EditorReplay` (no F prefix, no namespace) | **Succeeds** with `type: "EditorReplay"` |
| `MyReplaySelectWidget` (no U prefix, no `*`) | **Succeeds** with correct typed class |

The "succeeds but wrong" case (`UMyReplaySelectWidget*`) is the most dangerous — compile passes, but BPIR `call Member(Target: $MyVar, ...)` fails to resolve member functions because the variable's stored type is the untyped `object`, not the specific class. Had to remove and re-add the variable to fix it.

**Workaround:**
Strip F/U/A prefixes and trailing `*` before passing — bare identifier only. Verify the returned `type` field matches the expected class after add.

**Proposal:**
Route `variableType` through the same `ResolveUClass` / `ResolveUScriptStruct` helpers that `E-class-name-format-inconsistency`'s fix unified for other handlers. Accept all forms uniformly:
- `MyReplaySelectWidget`, `UMyReplaySelectWidget`, `UMyReplaySelectWidget*`, `/Script/App.MyReplaySelectWidget` → same object-typed `MyReplaySelectWidget*` variable
- `EditorReplay`, `FEditorReplay`, `struct:EditorReplay`, `/Script/App.EditorReplay` → same `FEditorReplay` struct
Reject with a clear error rather than silently falling through to the wildcard `object` type when resolution partially succeeds.

**Fix:**
The structured BPIR tokenizer (`IrTypeSpecParser::FCursor::ReadIdentifier`) only consumes `[A-Za-z_][A-Za-z0-9_]*`, so any `/`-leading string fails to parse before the runtime resolvers run — leaving the path-aware `ResolveUClass`/`ResolveUScriptStruct` (which DO handle `/Script/` and `/Game/` paths) unreachable from this entry point. Add a localized pre-parse branch in `BlueprintHandlerUtils::MakePinTypeFromBpirText` that, when the (optionally `class:`/`object:`/`struct:`-prefixed) input is `/`-leading, calls `ResolveUClass`/`ResolveUScriptStruct` directly and builds the `PC_Object` / `PC_Struct` pin type, biasing class-vs-struct order by the keyword prefix. This keeps the load-bearing shared IR grammar untouched. A covering regression test (path-form case) exercises the production `MakePinTypeFromBpirText` so the `#3` matrix gap can't regress silently again.
