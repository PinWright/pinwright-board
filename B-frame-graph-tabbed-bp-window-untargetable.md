# editor.frame_graph / screenshot_window can't target a specific BP in a tabbed window

Several open Blueprint editors dock as tabs in ONE `SWindow` whose title mirrors only the *active* tab. The shared window selector matches by title **substring** over top-level windows only (`DriveEditorChrome.cpp:245`, `Window->GetTitle().ToString().Contains(Selector.Title)`), and `editor.frame_graph` grabs the **first** `SGraphEditor` in that window's live tree (`FindGraphEditorRecursive`, `EditorWindowHandlers.cpp:147/294`) — which is the active tab's graph. The `FindGraphEditorViaTabs` fallback (`EditorWindowHandlers.cpp:175-202/301`) only runs when the active tab has no graph at all, and it too returns the first graph tab it finds with **no asset-path filter**, so it still can't pick a named BP. Once the window title reverts to the previously-active tab, `frame_graph{window_title:"BP_X"}` frames the wrong graph (or returns `NODES_NOT_FOUND` for BP_X's node ids) and `screenshot_window{window_title:"BP_X"}` returns `WINDOW_NOT_FOUND`. No selector names a specific asset's graph tab, and there is no bring-this-asset's-tab-to-front step, so capturing a non-active BP's graph is unreliable.

**Workaround:** close the other BP editors so the target BP is the sole tab — its name then owns the window title and it is the active/only graph.
**Fix:** add per-asset targeting — a selector that resolves the `SDockTab` whose graph belongs to a given asset path (activate it, then frame/capture), or an explicit bring-graph-to-front verb.

(2) In-band workaround (verified in source): `editor.open_asset` → `OpenEditorForAsset(Asset)` (`EditorCommandHandler.cpp:406`) focuses/activates the target asset's existing toolkit tab (cf. test comment `TestAssetDumpWidgetScreenshot.cpp:219` "OpenEditorForAsset early-returns when an editor is already open"), bringing its major tab to the front in the shared SWindow; then `frame_graph`/`screenshot_window` with NO selector resolves the ACTIVE top-level window (`DriveEditorChrome.cpp:259-281`) = the just-activated target, whose graph is now the first SGraphEditor found (`:294`) and whose name owns the title. (3) The reporter's own trace corroborates this: after `open_asset` `list_windows` showed idx1 title="BP_TimelineFade" (target WAS activated). NODES_NOT_FOUND fired WHILE the title matched — so the window was found and a graph WAS framed, but the 4 timeline-compile GUIDs weren't in it (Timeline compile nodes live in a hidden sub-graph), which is a wrong-nodeIds symptom, not an untargetable-graph one; the later `screenshot_window` WINDOW_NOT_FOUND is a title-reversion race (an intervening activation flipped the active tab back to BP_ScoreBus), avoidable by capturing the active window immediately after `open_asset` rather than re-selecting by the now-stale title. (4) Multiple BP editors docked into ONE SWindow is a non-default, self-inflicted layout — by default each asset editor opens in its own top-level window whose title IS the asset name, where title targeting works. (5) The proposed "fix" is a new capability (an asset-path dimension on the shared `FDriveWindowSelector`/`ParseWindowSelector`/`ResolveWindow`, load-bearing across ALL drive.*/editor.* window verbs, or a whole new bring-graph-to-front verb) — meaningful churn/risk in load-bearing targeting code for a niche case that already has a clean in-band path. Not a defect; closing as wontfix.
