# `sequence(N)` produces N+1 output exec pins (off-by-one), and round-trips are non-idempotent

The BPIR `sequence(N)` keyword is documented (`bpir.examples.sequence`, `bpir.instructions` §2.x) as
`sequence(3) [0 -> @s0, 1 -> @s1, 2 -> @s2]` — i.e. the count argument `N` is the number of
output exec pins, indices `0..N-1`. The compiler instead allocates **N+1** pins on the
`K2Node_ExecutionSequence` it creates: requesting `sequence(3)` yields a node with
`then_0, then_1, then_2, then_3`, where `then_3` is **dangling (unwired)**.

The defect is on the **count argument**, independent of how many targets are wired: `sequence(N)`
with any number of wired branches produces `N+1` pins. It is the compiler that over-allocates —
the decompiler faithfully reports the pin count it finds, so it emits `sequence(N+1)`.

Two consequences:

1. **The produced graph does not match the authored intent** — a spurious dangling exec output
   appears on every Sequence node. The compile returns `success: true` with `errors: []`,
   `warnings: []`, so the off-by-one is silent.
2. **Round-trip is non-idempotent / monotonically grows.** The compile_bpir wiki explicitly
   recommends "decompile an existing graph and adapt the output" as the way to learn/extend a
   pattern. Because decompile emits the real count `N+1`, feeding that text back through
   compile_bpir produces `N+2` pins, decompiling to `sequence(N+2)`, and so on — each
   decompile->recompile cycle adds one more dangling `then_*` pin to the Sequence node.

A dangling Sequence exec output is a runtime no-op (the three intended branches still fire in
order), so there is no execution corruption — but the graph accrues junk pins and the readback
count drifts away from what was authored.

## Repro (mcp__pinwright__call, verbatim)

1. `blueprint.create` `{name:"BP_SeqReplay", parentClass:"Actor", savePath:"/Game/Fuzz", waitForCompletion:true}`
2. `blueprint.compile_bpir`
   ```
   {"assetPath":"/Game/Fuzz/BP_SeqReplay","mode":"append","code":
   "entry event BeginPlay() {\n    %seq = sequence(3) [0 -> @a, 1 -> @b, 2 -> @c]\n@a:\n    call PrintString(InString: \"a\")\n@b:\n    call PrintString(InString: \"b\")\n@c:\n    call PrintString(InString: \"c\")\n}"}
   ```
   -> `{"nodeCount":5,"errors":[],"warnings":[],"compiled":true,"success":true}`
3. `blueprint.graph.get_nodes {assetPath:"/Game/Fuzz/BP_SeqReplay", graphName:"EventGraph"}` — the
   `K2Node_ExecutionSequence` node has **four** Output exec pins:
   ```
   "then_0" -> PrintString a
   "then_1" -> PrintString b
   "then_2" -> PrintString c
   "then_3" -> linkedTo: []          <-- spurious dangling pin (only sequence(3) was authored)
   ```
4. `blueprint.decompile {assetPath:"/Game/Fuzz/BP_SeqReplay", graphName:"EventGraph"}` reports
   `%n0 = sequence(4) [0 -> @s0, 1 -> @s1, 2 -> @s2]` — count drifted 3 -> 4.

Off-by-one is systematic and round-trip growth confirmed in the same session:
- authored `sequence(2) [0,1]`  -> decompiles `sequence(3)` (3 pins, then_2 dangling)
- authored `sequence(3) [0,1,2]` -> decompiles `sequence(4)` (4 pins, then_3 dangling)
- authored `sequence(4) [0,1,2]` (the prior decompile output) -> decompiles `sequence(5)` (5 pins, then_3+then_4 dangling)

## Expected

`sequence(N)` should allocate exactly `N` output exec pins (`then_0 .. then_{N-1}`). A fresh
`sequence(3)` should produce a 3-output Sequence node with no dangling pin, and
`blueprint.decompile` should round-trip the authored `sequence(3)` back to `sequence(3)`
(idempotent decompile->recompile). Likely a `<=` vs `<` / `N` vs `N-1` in the Sequence
exec-pin-allocation loop in the BPIR compiler (the same add-pin path described in the
compile_bpir wiki "Sequence node — exec pin auto-creation" note, which targets index `N` instead
of the highest required index `N-1`).
