# editor.screenshot success path hangs under PIE — OnScreenshotCaptured never fires for the game/PIE viewport

When a game/PIE viewport is active (`GEngine->GameViewport` non-null — the very case `editor.screenshot` advertises it prefers), the handler binds `GEngine->GameViewport->OnScreenshotCaptured()` and kicks `FScreenshotRequest::RequestScreenshot`, then waits for the delegate. Under PIE-in-editor that delegate path does not reliably fire, so the job's `OnComplete` never runs and the job sits in `running` indefinitely. No PNG is written. Replayed live twice (#4/#5), each polled to 86-90s with only a `started` event in jobs.jsonl.

The sibling `ui.screenshot` handler captures the SAME `GEngine->GameViewport` under PIE synchronously via `Viewport->ReadPixels` (UiHandler.cpp:137-160) and succeeds — proving the viewport is valid under PIE and only the async-delegate capture path is broken.

**Fix:** Make the game/PIE branch synchronous: read the game viewport's pixels with `Viewport->ReadPixels`, encode and save the PNG to `Saved/Screenshots/<filename>` (the proven `ui.screenshot` mechanism), and complete the job immediately with `{width, height, path}` — instead of binding the never-firing `OnScreenshotCaptured` delegate plus a 30s watchdog ticker. The level-editor-viewport fallback (no `GameViewport`) already completes synchronously and is unchanged.

**Files:** `Source/EditorAutomationRpcGateway/Private/Handlers/Editor/ViewportHandler.cpp` (the `editor.screenshot` handler, PIE branch at ~ViewportHandler.cpp:402-439).
