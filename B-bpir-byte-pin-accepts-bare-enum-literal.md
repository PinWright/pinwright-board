# BPIR accepts bare enum-name literal on bare-byte pin; produces graphs that fail BP compile later

`call EqualEqual_ByteByte(A: $Mode, B: Specific)` where `$Mode` is `enum<EAnalyzerLapMode>` and `Specific` is one of its values: BPIR places the node, writes the literal string `"Specific"` into pin `B`'s `DefaultValue`, and reports `compiled: true`. The B pin is `PC_Byte` with **no** `UEnum` subcategory at default-set time (`EqualEqual_ByteByte`'s declared signature; subtype only propagates from the A↔B link). The next full BP recompile rejects with `The current value (Specific) of the ' B ' pin is invalid: Expected a valid unsigned number for a byte property`.

This is distinct from `B-enum-raw-integers` (`#9`/`#10` DONE), which fixed the **qualified** form `EnumName::Value` via the `Value.Contains("::")` branch in `CodePinResolver::SetPinDefaultValue` (`Source/PinWright/Private/Compiler/CodePinResolver.cpp:129`). The bare form `Specific` never enters that branch — it falls through to the generic `TrySetDefaultValue` at line 238, which writes it through unchecked. The byte-pin validator only flags it during a later full BP recompile (potentially triggered by an unrelated `compile_bpir` on a different function in the same BP), so the original BPIR call appears clean while leaving the graph in a latent broken state.

The documented three-case behavior is in `docs/wiki/bpir.instructions.md` (lines 302–306): case (2) — `PC_Byte` without UEnum subtype — should store numeric strings. A bare identifier with no enum context is neither numeric nor a typed `Enum::Value`. The resolver should reject it at BPIR-compile time and require the author to either qualify (`EAnalyzerLapMode::Specific`), explicitly convert via `enum_to_byte`/`switch_enum`, or use `EqualEqual_IntInt` after an enum→int conversion.
