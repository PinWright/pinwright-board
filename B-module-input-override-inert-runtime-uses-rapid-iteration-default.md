# The override pin is written, echoed, and never read

`niagara.set_module_input` reports success and echoes the value it wrote
(`value: "90.0"`, `linked: false`, a fresh `pinId`). `niagara.inspect {includeStack:true}` then
reports the input as `valueMode: "local", value: "90.0"`. Both are true statements about the
**graph**. Neither is true about the **compiled script**: for a module that already existed in the
emitter, a rapid-iteration constant `Constants.<Emitter>.<Module>.<Input>` survives at the module's
**template default**, is regenerated by every compile, and is what the running simulation reads.

`E-niagara-inspect-params-stale-after-override` records the same two-value split but calls it a
readback nit — "the edit is real (graphs aspect proves it)". That premise is wrong. The rendered
frame says the stale value is the effective one.

## Measured, live editor port 27145, UE 5.8, EAContentExamples58, 2026-09-07

`/Game/FPS/VFX/NS_Blood`, four emitters, each with one `SpawnBurst_Instantaneous`
(`/Niagara/Modules/Emitter/SpawnBurst_Instantaneous`).

| emitter | stack `moduleInputs[].value` | `systemUpdateRapidIteration` value | particles in the render |
|---|---|---|---|
| Drips | `"44.0"` (`valueMode: local`) | `Constants.Drips.SpawnBurst_Instantaneous.Spawn Count` = **1** | 1 |
| Spray | `"60.0"` (`valueMode: local`) | `Constants.Spray.…Spawn Count` = **1** | 1 |
| Mist  | `"16.0"` (`valueMode: local`) | `Constants.Mist.…Spawn Count` = **1** | 1 |
| Burst | `"1.0"`  (`valueMode: local`) | `Constants.Burst.…Spawn Count` = **1** | 1 |

The same pattern holds on `/Game/FPS/VFX/NS_Impact_Metal` (five emitters, every
`SpawnBurst_Instantaneous.Spawn Count` = 1 in the RI store) and on `/Game/FPS/VFX/NS_Impact_Concrete`
(stack says Chunks 9, Dust 10, Sparks 2; RI says 1, 1, 1).

### The render is the proof

`Saved/Screenshots/OpenLevel/r4_03_blood_plusY_40ms_120cm.png`, 1280x720, pinned
`exposure {mode:"fixed", ev100:2}`, 40 ms after spawn, camera ~120 cm. Differenced against the
same-pose control `r4_04_concrete_plusY_40ms_120cm.png` on red dominance (`R - max(G,B)`), the whole
frame contains exactly four connected components above the ground's own red noise:

```
area= 1761 x= 624- 690 y= 421- 460     <- the entire mist
area=  307 x=1044-1081 y= 432- 442
area=  279 x= 697- 747 y= 388- 397
area=  114 x= 784- 793 y= 454- 468
```

In the sky band above the horizon, where the background has no red at all, a threshold of
`redness >= 2` finds **two** components in the whole 730 x 120 px region. This is not "present but
faint": 120 authored particles are not on screen at any brightness.

The mist mass settles it independently. `Uniform Sprite Size Min/Max` = 5/11 cm and the mist's
velocity is 95 cm/s, so at 40 ms sixteen sprites would occupy ~15-20 cm and stack to near-opacity.
The measured mass is **6.7 x 4.0 cm at peak redness 16** — one sprite at its authored alpha of 0.5,
not sixteen.

### The asymmetry that names the mechanism

`Spray` carries a second burst, `SpawnBurst_Instantaneous001`, added later by `niagara.add_module`.
Its RI entries for `Age`, `Loop Count Limit` and `Spawn Group` are present; its entries for
`Spawn Count`, `Spawn Probability` and `Spawn Time` — the three inputs that carry an override pin —
are **absent**. On that module the override is the only source and it is live. On the four modules
that existed before the override was written, the RI entry persists and wins.

So the defect is not "overrides never work". It is that an override written onto a module whose
input already had a rapid-iteration constant does not displace it, and nothing in any response says so.

## Impact

Critical, and it is invisible from every read surface PinWright offers. Four consecutive VFX review
rounds on this project raised particle counts through this verb (`7 -> 44` drips, `60` spray,
`6 -> 16` mist) and produced no visible change, because none of those writes ever reached the
simulation. Reviews scored the result and the builder chased shading, materials and sort order for
three builds. Every `Spawn Count`, and every other input on a pre-existing module that has an RI
entry, is affected on every system in the package.

## Repro

```
niagara.inspect {assetPath:<system>, parametersOnly:true, parameterName:"Spawn Count"}
# note Constants.<Emitter>.SpawnBurst_Instantaneous.Spawn Count = 1
niagara.set_module_input {assetPath:<system>, emitter:<E>, entryId:"<E>:<id>",
                          inputName:"Spawn Count", value:90}
# -> success, value:"90.0", linked:false
niagara.compile {assetPath:<system>, force:true, wait:true}      # -> status "completed"
niagara.inspect {assetPath:<system>, parametersOnly:true, parameterName:"Spawn Count"}
# -> STILL 1
```

`niagara.clear_module_overrides` on the same module followed by a fresh `set_module_input` does not
change the outcome; nor does rewriting the input as `{link: "User.X"}` (the pin reports
`linked:true, parameter:"User.MistCount"` and the RI constant still comes back at 1).

## Diagnosis-blocking property

The tell is only visible by cross-reading two aspects of the same `niagara.inspect` and knowing
which one the runtime honours — and the wiki currently tells the caller the opposite
(`niagara.set_module_input` Notes: *"Do not verify by reading the input back from `niagara.inspect`'s
`parameters` aspect: that aspect reads the rapid-iteration store, which keeps the unchanged template
default"*). Following that instruction is what hid this for four rounds.

## Workaround in use

Write the value **into both**: the override pin with `set_module_input`, and the rapid-iteration
constant with `niagara.set_parameter {scope:"systemUpdateRapidIteration",
name:"Constants.<Emitter>.<Module>.<Input>", type:"int32", value:N}` — the RI write **must come
after the last compile**, see `B-niagara-force-compile-resets-rapid-iteration-values`.

## Fix directions

- `set_module_input` should push the literal into the matching rapid-iteration parameter when one
  exists for that input, or delete that parameter so the pin is the only source — the same
  reconciliation `SpawnBurst_Instantaneous001` got for free.
- Until then, `set_module_input` should not report bare success when a rapid-iteration constant for
  the same input survives with a different value; the response should carry the shadowing entry and
  its value.
- `niagara.inspect {includeStack:true}` should mark such an input as shadowed rather than reporting
  `valueMode: "local"` with a value the simulation will not use.

## Second encounter, 2026-09-07 08:00 UTC: the blast radius is not Spawn Count

A full sweep of all 13 systems under `/Game/FPS/VFX/` — every stack module input with
`valueMode: "local"` compared against the matching `Constants.<Emitter>.<Module>.<Input>` in every
rapid-iteration store — found **111 shadowed inputs across 13 systems**, of which only 38 are
`Spawn Count`. Spawn Count is the case that got noticed because its effect is countable; it is not
the case that dominates.

| shadowed input | count | authored -> effective |
|---|---|---|
| `InitializeParticle.Color` | 45 | e.g. `(40, 14, 2, 1)` -> `(1, 1, 1, 1)` |
| `SpawnBurst_Instantaneous.Spawn Count` | 38 | e.g. `34` -> `1` |
| `EmitterState.Loop Duration` | 13 | e.g. `0.25` -> `2` |
| `InitializeParticle.Lifetime` | 11 | e.g. `0.09` -> `2` |
| `SubUVAnimation.Start/End Frame Range Override` | 4 | `2`/`5` -> `0`/`63` |
| `InitializeParticle.Position Offset` | 1 | `(0,0,3)` -> `(0,0,0)` |
| `SpawnBurst_Instantaneous001.Spawn Time` | 1 | `0.035` -> `0` |

Every one of them is **switch-active**, checked against the module's own `staticSwitchInputs` rather
than assumed:

- `InitializeParticle.Color Mode` = `1` = **Direct Set** on 58 of 59 emitters
  (`/Niagara/Enums/ENiagara_ColorInitializationMode`), so `Color` is the live input. Every authored
  HDR tint in the package — muzzle-flash cores, sparks, embers, blood, and every alpha-authored
  smoke and mist — has been initialising to white at alpha 1.
- `InitializeParticle.Lifetime Mode` = `0` = **Direct Set**
  (`/Niagara/Enums/ENiagara_LifetimeMode`) on exactly the 11 emitters whose `Lifetime` is shadowed,
  so a 0.06-0.09 s muzzle light and a 0.6 s tracer have been living **2 s**.
- `EmitterState`: `Loop Behavior` = `1` = Once and `Loop Duration Mode` = `0` = Fixed, so
  `Loop Duration` is live; a 0.25 s glass flash has been running a 2 s loop.
- `SubUVAnimation`: `UseStartFrame` and `UseEndFrame` are both `True` on `NS_Impact_Water/Column`,
  so its authored 2-5 sub-image range has been playing 0-63.

So the correct statement of this ticket is not "Spawn Count was tuned four times for nothing" but
"**every literal an agent authored through `set_module_input` on a pre-existing module is inert**,
and the RI store has been serving module template defaults to the simulation for the whole life of
the package". The fix directions above are unchanged; the priority is not.

Two further facts from the same sweep:

- **The asymmetry generalises exactly as predicted.** Across the package, 620 stack inputs carry
  `valueMode: "local"` with **no** RI entry at all and are live; every module added by
  `niagara.add_module` (`SpawnBurst_Instantaneous001` on five emitters) has live `Spawn Count`,
  `Spawn Probability` and `Spawn Time` while its `Age` / `Loop Count Limit` / `Spawn Group` RI
  entries persist. Only inputs whose RI entry pre-existed the override are shadowed.
- **`/Game/FPS/VFX/NS_Blood` was not fully repaired.** Its three Spawn Counts are correct (90 / 110 /
  26), but `Drips`, `Spray`, `Mist` and `Burst` `InitializeParticle.Color` are all still shadowed by
  white, and `Burst.InitializeParticle.Lifetime` reads `0.08` in the stack and `2` in the RI store.
  The earlier repair fixed the input it was looking for, not the class of defect.

106 of the 111 were repaired this session by writing the authored value into the shadowing RI
constant with `niagara.set_parameter` (verified against the `.uasset` bytes on disk, not a
read-back); the 5 left are `NS_Blood`'s, which was out of the repairing agent's scope.
