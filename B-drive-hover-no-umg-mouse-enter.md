# drive.hover does not trigger UMG OnMouseEnter in PIE

PIE hosted in the level-editor viewport, `/Game/System/FrontEnd/Maps/L_Core`. `W_LobbyLoginButton` (a UUserWidget inside W_LyraFrontEnd) plays its `OnHovered` animation from `Event OnMouseEnter`. `drive.hover` on its `NickName` text (also on `tb_ProfileSub`, and after first hovering another button so there is a real enter transition) returns `no_change_within_budget`; `drive.observe` shows the dropdown buttons still translated off-screen; `drive.input_state` reports `slate_active:false` with the OS cursor at the element center. `drive.click` on the same surface works.

**Workaround:** a PIE-only Python poke calling `play_animation_forward(OnHovered)` on the live widget.

**Source (8748c637):** `drive.hover` (`DriveActionHandlers.cpp:172-202`) calls `FDriveInput::HoverAt` = `MoveTo` (`DriveInput.h:84`, `DriveInput.cpp:244-257`), which sets the OS cursor and sends one `ProcessMouseMoveEvent` (`DriveInput.cpp:117-140`). `os_input` is Linux/X11-only, so there is no alternative injection path on Windows.

**Related:** `B-drive-click-misses-pie-game-viewport` (OPEN) `#3` saw `drive.hover` inert alongside `drive.click` with PIE hosted in the level viewport; here clicks worked, so the mouse-capture explanation there does not cover this case. `B-drive-geometry-window-space-injected-as-desktop` (window-space vs desktop coordinates) is ruled out here because clicks at the same centers landed.

- `#3-synthetic-move-leave-hold` `IN-REVIEW` developer - **Root cause, from source; not reproduced live** (no editor was available to this fixer, and the suite's `-RenderOffScreen` editor runs `FNullApplication`, whose `IsCursorDirectlyOverSlateWindow()` is always true, so the leave cannot happen there). The injected move does reach the PIE viewport's Slate tree and fires `OnMouseEnter`; the hover is then lost one frame later. Every Slate tick runs `FSlateUser::SynthesizeCursorMoveIfNeeded` -> `ProcessMouseMoveEvent(.., bIsSynthetic=true)`, and for a synthetic move `bOverSlateWindow = IsActive() || PlatformApplication->IsCursorDirectlyOverSlateWindow() || GetHandleDeviceInputWhenApplicationNotActive()` (`SlateApplication.cpp:6414`). `FDriveInput::MoveTo` sets the inactive-input flag only inside its scope, so on the next frame, with the editor inactive (`#1`'s `slate_active:false`) and another application's window over the point (Windows `WindowFromPoint` is not a Slate window; Linux `bInsideOwnWindow` false), the synthetic move routes an empty `FWidgetPath` and `RoutePointerMoveEvent` sends `OnMouseLeave` to the whole previous path (`SlateApplication.cpp:5744-5810`). The enter animation reverses before the settle loop can see it. `drive.click` is unaffected because press and release complete inside one call; `#2`'s non-repro fits an editor not covered at the point (Blueprint vs native `OnMouseEnter` is irrelevant: both route through `SObjectWidget::OnMouseEnter` -> `NativeOnMouseEnter`). **Fix:** `FDriveInput::HoverAt` (no longer an alias of `MoveTo`) holds `SetHandleDeviceInputWhenApplicationNotActive(true)` after its move and registers a core ticker that restores the prior value once the platform cursor leaves the hovered point (user mouse or a later injection elsewhere); with the flag held, the synthetic move resolves the path through `LocateWindowUnderMouse`'s Slate-order fallback and the hover persists. `os_input` hover is unchanged (real OS input). Files: `Source/PinWright/Private/Handlers/Drive/DriveInput.h/.cpp`, `docs/wiki-src/drive.md` (`drive.hover`), `CHANGELOG.md`.
