# Refused macro recompile wipes caller pin defaults on linked inputs

When a `Replace` recompile of a same-Blueprint macro would change an existing caller pin (type,
removal, default or links), `ReconstructSameBlueprintMacroCallers` refuses it and the compiler rolls
back: `RollbackCreatedState` restores the macro graph, `ReconstructMacroCallersFromSnapshots`
rebuilds each caller, then `RestoreMacroCallerSnapshots` (`Compiler/BpirCompiler.cpp` ~1445) writes
each pin's snapshot `DefaultValue` / `DefaultTextValue` / `DefaultObject` and re-creates its links.

It re-created links with `Schema->TryCreateConnection`. `UEdGraphSchema::TryCreateConnection`
(`EdGraphSchema.cpp:521`) calls `PinConnectionListChanged` on both nodes, and
`UK2Node::PinConnectionListChanged` (`K2Node.cpp:518-531`) calls
`ResetPinToAutogeneratedDefaultValue` on any linked input pin. So every caller input pin that had
both a link and a default lost the default the line before had restored, and a peer input pin on
another node linked to a caller output lost its default too. The refused compile reports failure
while it has mutated the caller: the guard's promise is broken.

Repro: `PinWright.bpir.compiler.MacroRecompilePreservesCallerInstances` (UE 5.8), offscreen full suite
`Saved/Logs/pw_gapwave_full_offscreen2.log` line 20989: "Expected 'Value default survives failed
signature recompile' to be "5.0", but it was """. The `Value` pin is linked from `MakeLiteralFloat`
and carries default `5.0`. It was hidden until `B-macro-recompile-test-invalid-ir` made the test's
refused recompile reach the guard.

**Fix:** re-create the snapshot links with raw `UEdGraphPin::MakeLinkTo`. The links existed before
the refused recompile and the pins are back on their original types, so the links need no
validation, and the node notifications that reset defaults do not fire.
