# `create_blend_space_1d` has no grid-divisions param — axis min/max/grid live on a separate `set_axis_settings`, not signposted from the create call

A common user intent for a 1D blend space is "create a Speed axis blend space running 0..600 with ~4 grid divisions" — i.e. the axis name, range, and grid-division count are all part of *creating* the asset. But `create_blend_space_1d` exposes none of these: the axis grid-division count (and the canonical axis min/max) live on a **separate** `set_axis_settings` call that must run after the create. The `create_blend_space_1d` doc carries no grid-divisions parameter and no inline pointer telling the caller that grid/range tuning is a follow-up `set_axis_settings` step.

The only signpost today is the namespace **Workflow gotchas** note (`animation.authoring.md:24`): *"Blend-space samples cannot be added until `set_axis_settings` has run (axes define the sample coordinate space)."* That note exists to explain the **ordering** dependency (you cannot `add_blend_sample` before `set_axis_settings`), and a careful reader can infer from it that axis/grid config is owned by `set_axis_settings` — but it never states the property split explicitly: that `gridDivisions` / axis min/max are `set_axis_settings` params, not `create_blend_space_1d` params. A caller who reads only the `create_blend_space_1d` method doc (the natural first stop for "create a 1D blend space with N grid divisions") finds no grid-divisions param and no breadcrumb to where it lives.

This is a discoverability gap, not a tool bug: the sequence `create_blend_space_1d` → `set_axis_settings` (Speed 0..600, gridDivisions=4) → `add_blend_sample` ×N works correctly and the agent completed it on the first try by leaning on the gotchas note. The cost is that the create-call doc and the set_axis_settings doc do not cross-reference for the grid/range knobs, so the discovery hinges on the reader connecting the ordering gotcha to "...therefore grid divisions must be a set_axis_settings param."

This is a distinct angle from `E-get-animation-info-thin-on-blend-space` (which is about read-*back* parity — `get_animation_info` returning only `numSamples`). This ticket is about the *authoring*-side discoverability of where the grid-divisions/axis-range parameters live relative to the create call.

**Workaround:** after `create_blend_space_1d`, call `set_axis_settings` with the horizontal axis name + min/max + `gridDivisions` before `add_blend_sample`; the namespace Workflow-gotchas note hints at the ordering.

**Fix (docs):** In `docs/wiki-src/animation.authoring.md`, add an explicit one-liner to the blend-space sub-workflow bullet (line 13) and/or the `create_blend_space_1d` method section stating that the axis name, min/max range, and **grid-division count are configured via `set_axis_settings` after creation** (not on the create call), and have `create_blend_space_1d`'s doc cross-reference `set_axis_settings` for axis/grid tuning. Optionally promote the existing Workflow-gotchas sentence (line 24) to name the grid-divisions param explicitly so a reader landing on the create doc is told where range/grid live.
