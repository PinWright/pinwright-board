# level.save returned {started:true} with no completion signal

`level.save` triggered a level save and returned `{started:true}`. Save operations involve disk I/O and may trigger source control hooks; callers had no confirmation that the save had completed before issuing further edits.

**Fix:** Handler now calls `Ctx.StartJob()` and wraps the save call in an `AsyncTask(ENamedThreads::GameThread, ...)` that calls `FEditorFileUtils::SaveLevel`, then calls `FJobRegistry::CompleteJob` with `{saved: true/false}` from the result.

**Files:** `Source/PinWright/Private/Handlers/Level/LevelHandler.cpp:299`.

## History

- `#2-asynctask-wrap` `IN-REVIEW` developer — Migrated to `Ctx.StartJob()`. `AsyncTask` wraps the synchronous save call; on return `CompleteJob` is fired with the save result.
- `#3-verified-saved-payload` `DONE` tester — Verified end-to-end: kicked `level.save` → ticket `j_20260427T023602_1eb68a46` with `packageName:"/Game/System/FrontEnd/Maps/L_Core"`. `system.job_status` ~1.2 s later returned `status:"completed"` with `result:{saved:true}`. jobs.jsonl recorded `started` + `completed` events with matching payload.
- `#4-root-cause-wrong-drive-write` `DONE` reporter — Informational correction from an external finding; **no status change** (see the end of this entry). The level-save ticket family concluded that saves reporting success wrote no `.umap` anywhere; that conclusion was wrong, because the on-disk searches behind it were scoped to `Content/`. The packages were being written, to a drive-relative path outside the project: `FEditorFileUtils::SaveLevel`/`SaveMap` take a *filesystem filename*, which the engine forwards as `ForceFilename`, and the plugin passed a long package name (`/Game/...`), so `FPaths::IsRelative` read the leading `/` as already-rooted and Windows resolved it against the current drive, landing an extensionless package at `C:\Game\...`; the save genuinely succeeded, so the engine cleared the dirty flag. Evidence: `C:\Game` held **824 orphan package files, 25 MB, oldest mtime 2026-02-28**, all carrying the `PACKAGE_FILE_TAG` magic bytes `c1 83 2a 9e` — 786 `__EARG_LightingLevelHonestyProbe_*` and 38 named after probe maps from sibling investigations. **This ticket's own probe map is not among the recorded names:** the only map in its history is `/Game/System/FrontEnd/Maps/L_Core` from the `#3` verification (job `j_20260427T023602_1eb68a46`), which does not appear in the `C:\Game` list, so the name-overlap evidence does **not** attach to this ticket and nothing here should be read as proof that this ticket's save wrote to `C:\Game`. The mechanism does attach, though: `#3` treated `result:{saved:true}` as proof the save completed, and under the `#2` implementation that boolean came straight off `FEditorFileUtils::SaveLevel`'s return for a long package name — exactly the value the path defect made unreliable. `L_Core` is also a pre-existing on-disk map, which makes it the case `40f26b6a` calls out separately: the disk gate checked only that a `.umap` existed, not that *this* save wrote it, so a stale file from an earlier legitimate save satisfied the check and a wrong-path write would stay invisible on an already-saved map. Fixed in `pinwright-ue-dev` `40f26b6a` ("Save levels to the resolved filename, not the package path"): `McpSafeLevelSave` resolves the package via `ResolveLevelPackageToMapFilename` and proves the destination against the engine's `OutSavedFilename`; `level.create` carried a second independent instance fixed in the same commit; and the existence-only gate gained a pre-save timestamp/size freshness check. `level.save` routes through both today — the handler `#2` patched has since been consolidated out of `SaveLevelHandler.cpp` into `Handlers/Level/LevelHandler.cpp`, where the job body calls `McpSafeLevelSave` and re-gates its `saved` field through `VerifyLevelSavedToDisk` (`:317-330`). Verified by a full UE 5.8 automation run, 3496/3496 green, with `C:\Game` holding 824 files before the run and 824 after; the tree has since been deleted. **`status:` deliberately left `DONE`** — this is a correction to the record, not a transition — but note the `DONE` rests on `#3`, whose sole success evidence was that unreliable `saved:true`, so this ticket still needs its own re-verification against the fix: kick a `level.save` and confirm the completed job's `{saved:true}` now corresponds to a *freshly written* `.umap` at the resolved project path. Re-read the `#2` fix in the same light — it may have been aimed at the wrong layer: wrapping the save in `Ctx.StartJob()`/`AsyncTask`/`CompleteJob` addressed the completion-signal question correctly, but the payload it reports was sourced from a return value that was `true` while the file could be going to another drive, so the signal it added was honest about *when* the save finished and silent about *where* it went.
