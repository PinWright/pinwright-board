# `compile_bpir` never wires cross-label fall-through (auto-chain to the next adjacent label)

## Symptom

`compile_bpir`'s exec-wiring pass (`WireExecPins`) **never emits a cross-label
fall-through exec edge**. The documented `bpir.instructions` §2.8 idiom — a label
block with no terminator "falls through to the next adjacent label (auto-chain)" —
compiles with `compiled:true, success:true, errors:[], warnings:[]`, but the block's
terminal exec node is left with a **dangling exec output** and the next label's entry
node never receives that predecessor. At runtime the fall-through path silently never
reaches the next block. Pure silent control-flow corruption on a normal, documented
authoring path.

This is **unconditional**: it does NOT require a branch, a sibling block, or the
target exec pin being pre-wired by a preceding explicit `exec ->`. A plain sequential
two-label body with no branch and no explicit jump anywhere ALSO drops every
cross-label fall-through edge (see repro #12). The two exec paths that DO wire
correctly are (a) intra-block auto-chain (impure nodes within one `@label:` segment)
and (b) explicit `exec -> @label` / `[pin -> @label]` jumps — the §2.8 documented
"auto-chain to next label" is the only one dropped.

This is the canonical pattern from `call("bpir.instructions")` §2.8 and
`call("bpir.entry-points")`:

```
@then:
    call PrintString(InString: "Yes")
    exec -> @done                   # explicit jump
@else:
    call PrintString(InString: "No")
    # Falls through to @done (next label, auto-chain)
@done:
    call PrintString(InString: "After branch")
```

Expected graph: `@then.Print.then -> @done.Print.execute` **and**
`@else.Print.then -> @done.Print.execute` (two predecessors on the tail). Actual
graph: only the `@then` edge is made; the `@else` fall-through edge is dropped.

## Scope (corrected — see repro #12)

The trigger is NOT "a fall-through edge whose target exec input pin is already linked
by a preceding explicit `exec ->`". `WireExecPins` builds independent label segments;
every label segment is created with `IncomingExecPin = nullptr` (Step 1) and Step 2
seeds `LastExecOutput = Segment.IncomingExecPin` at every segment start, then throws
it away at the segment's end. A segment's terminal exec output is therefore NEVER
connected to the next label's first node — the fall-through edge is simply never
attempted, regardless of whether the target pin was pre-wired.

| Shape | Cross-label fall-through edge | Verdict |
|---|---|---|
| intra-block sequential (impure nodes within one `@label:`) | emitted | correct |
| explicit `exec -> @label` / `[pin -> @label]` jump | emitted | correct |
| block with no terminator → next adjacent label (§2.8 fall-through) | **never emitted** | **BUG** |

The original "Isolation (the crux)" table that marked the no-sibling / not-pre-wired
shapes as `correct` was wrong: a virgin target exec pin receives no fall-through edge
either. Reproduces in both positioned (`@(x,y)` on every node) and auto-layout modes —
positioning is not the trigger.

## Why this is not `B-bpir-decompile-shared-tail-absorbed-into-branch` (DONE)

That ticket is **decompile-side**: it states "The compiler is fine. The graph the
compiler builds from the original BPIR is correct (two predecessors fanning into one
successor — standard reconvergence)" and fixes `BpirDecompiler.cpp WalkExecChain` label
naming. This finding contradicts that premise: the **compiler** itself now produces a
one-predecessor graph for the explicit+fall-through shape (the very shape that ticket's
repro used as input). The fix surface is the compiler's exec-wiring / auto-chain
fall-through path (`WireExecPins` family in `BpirCompiler.cpp`), not the decompiler.
Distinct from `B-bpir-statement-cast-success-unwired-replace-shared-topology` (needs a
`cast` + cross-entry shared K2Node topology) and `B-bpir-exec-target-leads-pure-node`
(loud `COMPILE_FAILED`, pure node leading a label). This one is silent, single-entry,
fresh-asset, no cast required.

## Fix

In `WireExecPins` Step 2 (`BpirCompiler.cpp`), carry each label segment's trailing
`LastExecOutput` into the next segment's `IncomingExecPin` so an open-ended block falls
through to the next adjacent label. The intra-segment chain already collapses
`LastExecOutput` to `nullptr` at every terminator (a multi-output branch/switch node, an
explicit `exec ->`/`ExecGoto`, or a node with no exec output such as `return`), so a
terminated segment carries a null pin and emits NO fall-through edge — only a genuinely
open-ended block reconverges into the next label. The carried fall-through edge and any
explicit `exec -> @merge` from a sibling land on the same exec input pin as two
predecessors, giving correct reconvergence. This makes the compiler match the wiki §2.8
and corrects the stale `docs/bpir-compiler-internals.md` "auto-chain does NOT happen
across label boundaries" note.
