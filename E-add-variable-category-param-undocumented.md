# `add_variable` / `set_variable_settings` `category` param is undocumented on `blueprint.md`

The `category` parameter on `blueprint.add_variable` and `blueprint.set_variable_settings` is advertised in the handler param specs (`BlueprintPropertyHandler.cpp:39`, `:631`) but the blueprint wiki overlay (`docs/wiki-src/blueprint.md`) does not mention `category` at all — not its existence, not its accepted format, and not where category-setting belongs (add-time vs. `set_variable_settings` vs. `set_variable_metadata`). The overlay also has no `### blueprint.add_variable` / `### blueprint.set_variable_settings` / `### blueprint.set_variable_metadata` sections, so a caller reading the wiki has no place that explains the `category` contract.

`category` is an **editor-only organizational label** — the heading a variable groups under in the Blueprint editor's Variables panel. It takes a **plain string**: both handlers build the category FText with `BlueprintHandlerUtils::MakeBlueprintCategoryText` (`return Category.IsEmpty() ? FText::GetEmpty() : FText::FromString(Category)`, `BlueprintHandlerUtils.cpp:2599`), called at `BlueprintPropertyHandler.cpp:151` (`add_variable`) and `:828` (`set_variable_settings`). The same label is equivalently writable via `blueprint.set_variable_metadata` key `Category`. This is a downstream wiki edit, not a code change.

**What it should do:** document on `docs/wiki-src/blueprint.md` (under `### blueprint.add_variable`, `### blueprint.set_variable_settings`, and `### blueprint.set_variable_metadata`) that `category`:
- is an optional, editor-only organizational label (the Variables-panel grouping heading), with no effect on runtime behavior;
- accepts a **plain string** (e.g. `"Minimap"`); empty/omitted leaves the variable uncategorized;
- can be set at add time, later via `set_variable_settings`, or equivalently via `set_variable_metadata` key `Category`.

**Fix:** add the three H3 sections to `docs/wiki-src/blueprint.md` documenting `category` as above. Do **not** mention the old `NSLOCTEXT(...)` / `INVALID_TEXT_LOCALIZATION_IDENTITY` workaround — that rejection no longer exists (the companion code bug `B-variable-category-ftext-localization-error` is fixed, IN-REVIEW; plain strings are now accepted).

**Note (history — pre-fix):** this ticket was originally filed alongside the FText-coercion bug `B-variable-category-ftext-localization-error`. At filing time a plain-string `category` was rejected with `INVALID_TEXT_LOCALIZATION_IDENTITY` and the discovered workaround was to pass `NSLOCTEXT("ns","key","Source")` (the original authoring task — `/Game/Pickups/BP_HealthPickup` — burned ~2 failed calls plus a cross-namespace detour to `property.set.md` learning that workaround). That bug is now fixed: `MakeBlueprintCategoryText` builds the category from the plain string directly, so the workaround is obsolete and must NOT be documented.
