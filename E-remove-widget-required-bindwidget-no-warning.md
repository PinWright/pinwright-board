# widget.remove_widget / rename_widget invalidate a required BindWidget target with no advisory field

`widget.remove_widget` deleting child `Settings_Panel` — the variable that satisfies a REQUIRED `meta=(BindWidget)` property `UGameSettingPanel Settings_Panel` on the widget's C++ parent chain (`UGameSettingScreen`, a base of `ULyraSettingScreen`) — succeeds and returns `{"success":true, "cascadedBoundEventsRemoved":0}` with no field indicating a required bind was invalidated. The removal is CORRECT and `success:true` is honest — the widget really is gone; there is no data corruption and no silent-wrong readback. The only cost is that a foreseeable destructive consequence is not surfaced at mutation time: it is reported clearly, and specifically, by the very NEXT `blueprint.compile`: `A required widget binding "Settings_Panel" of type Game Setting Panel was not found.` (the engine's own required-bind check, `WidgetBlueprintCompiler.cpp`, names the exact widget and type). So this is pure friction — an autonomous agent pays one extra remove→compile→diagnose→re-add round-trip instead of being told up front. An advisory field on the mutation result closes that loop in-session.

`widget.rename_widget` shares the IDENTICAL gap: renaming the variable that satisfies a required bind (so it no longer matches the bind name) breaks the same bind with no advisory either. `widget.reparent_widget` does NOT — reparenting preserves the variable name, and BindWidget matches by name+type, not tree position.

The handler (`Source/PinWright/Private/Handlers/UI/WidgetHierarchyHandler.cpp`) finds the widget by name (`remove_widget` line 172 / `rename_widget` line 257) and removes/renames it (lines 188 / 266) without ever checking whether the affected variable name matches a required `meta=(BindWidget)` property on the generated-class parent chain. No helper in the plugin enumerates required BindWidgets; the parent-class metadata is available at mutation time (`FWidgetBlueprintEditorUtils::IsBindWidgetProperty` / a `HasMetaData("BindWidget")` walk of `WidgetBP->ParentClass`).

**Why Low, not Medium:** nothing is blocked — the removal/rename succeeds, no workaround is needed to accomplish the task, and the consequence is reported by the next compile with a precise, actionable, named error (no source dive, no editor restart — a compile error is readable live). Per the board rubric that is pure friction (Low), and the reach modifier bumps down further because a removed/renamed widget matching a C++ *required* bind is a rare edge path (most mutated widgets are not C++-bound). The `silent-success` framing is dropped: the breakage is loud at the next compile, not silent.

**Workaround:** Before removing, reparent the widget off the required bind (rename the variable so it no longer matches — though rename has the same gap) or keep a placeholder widget under the bound name so the binding stays satisfied. In practice, just read the next `blueprint.compile` error, which names the broken bind.
**Fix:** In the remove and rename handlers, walk `WidgetBP->ParentClass` for object properties of a `UWidget` type carrying `BindWidget` (required) metadata — excluding `BindWidgetOptional` / `OptionalWidget` (optional binds never fail compile). If an affected variable name (the removed widget + its cascaded descendants, or the old name for rename) matches a required bind, surface an ADVISORY field in the result — `removedRequiredBinds` / `renamedRequiredBinds`, an array of `{name, type}`, always present (empty when nothing broke) — plus a human-readable `warning` string when non-empty. Never hard-refuse: removal/rename of a bound widget is a legitimate operation (e.g. the DONE cascade flow `E-widget-remove-widget-cascade-bound-events` strips whole subtrees), so the earlier "refuse unless an override flag is passed" idea is rejected as a breaking change to a load-bearing mutator.
