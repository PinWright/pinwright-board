# blueprint.graph.find_orphaned_nodes returns 0 while BPIR decompiler still reports orphan warnings on the same asset

After running `blueprint.graph.find_orphaned_nodes` (with `dryRun: false, includeDataOnly: true`) across all graphs of `/App/HELIOS/Framework/HELIOS_BP` and getting `orphanedCount: 0, deletedCount: 0`, an immediate `asset.dump diff:true` on the same asset still emits orphan warnings in the BPIR `# ==== Warnings ====` section:

```
Orphaned node not reachable from any entry point: Reroute Node      (×6)
Orphaned node not reachable from any entry point: Construction Script
```

The two tools have different definitions of "orphan":

- `blueprint.graph.find_orphaned_nodes` (graphsScanned: 16) reports 0.
- BPIR decompiler reports 7 (6 reroute knots + 1 "Construction Script").

This is not a regression introduced by the user's edits — it reduces from 14 in the baseline to 7 after a deletion sweep. But the residual 7 are invisible to `find_orphaned_nodes`, so a workflow that relies on the orphan finder as a "before save" gate (per the corruption-avoidance memory `feedback_mcp_bp_corruption_avoidance.md`) leaves BPIR-visible junk in the asset.

**Reproduce:**

1. On any non-trivial Blueprint that has dangling reroute knots or composite-graph residue, call `blueprint.graph.find_orphaned_nodes` with `dryRun: false, includeDataOnly: true` (no `graphName` to scan all).
2. Result: `orphanedCount: 0`.
3. Call `asset.dump <bp> diff:true` (or any decompile path that emits the `# ==== Warnings ====` block).
4. Result: warnings list contains "Orphaned node not reachable from any entry point" lines that point at nodes the finder did not see.

Confirmed on `/App/HELIOS/Framework/HELIOS_BP.HELIOS_BP` after a multi-step deletion of 9 functions and ~14 call/variable nodes. `find_orphaned_nodes` swept correctly during the cleanup (deleted 2 nodes in `Activation Node`), but the BPIR decompiler still finds 6 reroute knots and 1 "Construction Script" entry that the finder ignores.

## Root cause

The original knot/empty-construction-script disagreement was corrected by the earlier shared walk, but a blanket structural-node exclusion later removed all knots from `includeDataOnly:true` results. The graph-qualified nested-orphan production path was already correct: the automation log shows its expected orphan-warning count passed and the finder produced one key. The new test searched BPIR's hyphenated warning GUID with the finder's compact JSON GUID form, so its locally reconstructed BPIR set was empty despite the warning being present.

## Fix

Use one authored graph-family model for both consumers. Reachability keys are `(authored graph, NodeGuid)`, with one shared seed set and output-exec BFS; `includeDataOnly` extends that result backward through linked non-exec inputs, and the standalone-pure round-trip exception is explicit model metadata. Finder and delete scans consume the model directly. A named read-only finder and BPIR decompile scan the selected graph's transitively nested authored child graphs. Named deletion mutates only the selected graph by default; `includeNestedGraphs:true` opts into deleting nested child-graph orphans and the response reports `nestedGraphsSkipped`. BPIR builds the model before cloning/flattening, maps clone nodes to exact authored source keys only for emission bookkeeping, and emits warnings from the authored source family; flattening remains presentation-only. The shared exit-tunnel predicate excludes graph boundaries from both warning paths. Node shape is cached once per graph-qualified key, and the backward data closure is skipped for `includeDataOnly:false` or families without a non-standalone pure candidate; BPIR requests it only when its warning contract needs those pure candidates.

Implementation: `BlueprintHandlerUtils::BuildBlueprintOrphanReachability` now owns graph-qualified exec/data sets, cached node shape, one shared orphan predicate, structural exclusions for comments, entries, and exit tunnels, and explicit standalone-pure preservation metadata. Knots remain reachability connectors and become candidates only in data-only mode; they cannot use BPIR's standalone-expression exception. `FindBlueprintOrphanNodes`, the graph handler's selected-family accounting, and BPIR warning generation consume the shared decision. BPIR's emission mapping remains keyed by exact authored `(graph, NodeGuid)` source keys with no global GUID fallback. The contract test now uses each consumer's actual GUID text format while comparing normalized compact keys.

Changed files:
- `Plugins/PinWright/Source/PinWright/Private/Handlers/Blueprint/BlueprintHandlerUtils.h`
- `Plugins/PinWright/Source/PinWright/Private/Handlers/Blueprint/BlueprintHandlerUtils.cpp`

Regression tests: `PinWright.bpir.decompiler.FinderAndDecompilerOrphanModelContract` invokes the production finder handler with the EventGraph `graphName` and `includeDataOnly:true`, then invokes `FBpirDecompiler::DecompileGraph` on one valid `BeginPlay -> composite -> inner -> exit -> outer` chain with a duplicate-GUID nested orphan and standalone-pure `IsValid` node. It compares the exact graph-qualified finder/BPIR orphan sets, requires the shared exit-tunnel exclusion, and requires standalone-pure preservation in emitted text. Reverting the shared exclusion or graph-qualified authored warning path makes the finder/BPIR set comparison fail. `PinWright.blueprint.graph.delete_orphaned_nodes.NamedGraphNestedScopeOptIn` invokes the production delete handler twice and proves the nested orphan survives the default selected-graph scope, then is deleted with `includeNestedGraphs:true`. Deliberate non-changes: `GraphWalker.cpp`, the existing standalone-pure serialization policy (including entryless pure-only behavior), composite boundary destruction, engine/config/Saved files, and runtime/build/test execution. Runtime, saved-asset, and compiled-Blueprint parity remain unresolved by this source-only verification.

## Impact

- Workflows that rely on `find_orphaned_nodes` as a pre-save integrity gate (per `feedback_mcp_bp_corruption_avoidance.md` rule 3) get a false "all clean" signal. Junk knots persist in the saved `.uasset`.
- BPIR decompile output is noisier than necessary, mixing real residual orphans with previously-observable warnings.
- Differential diff workflows comparing baseline → post-edit struggle to distinguish "bug we cleaned up" from "bug that still lingers".

## Workaround

None reliable inside MCP today. The asset can be opened in the editor and the dangling knots manually deleted, then re-saved.
