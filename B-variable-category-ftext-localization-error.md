# `add_variable` / `set_variable_settings` reject `category` with INVALID_TEXT_LOCALIZATION_IDENTITY

Passing the documented `category` parameter to `blueprint.add_variable` or `blueprint.set_variable_settings` fails with `INVALID_TEXT_LOCALIZATION_IDENTITY`. Both handlers route the category string through `CoerceStringToPersistedFText` (`PropertyImport.cpp:201`), which only accepts a value that already carries a localization namespace+key (`NSLOCTEXT(...)`), is string-table-backed, or inherits identity from an existing localized value; a plain string like `"Minimap"` matches none and falls through to the error return at `PropertyImport.cpp:237`. The handler call sites are `add_variable` at `BlueprintPropertyHandler.cpp:151-156` (`NewVar.Category = MoveTemp(CategoryText)`) and `set_variable_settings` at `BlueprintPropertyHandler.cpp:783-792`. `category` is advertised in both param specs (`BlueprintPropertyHandler.cpp:39`, `:584`) and the wiki, so this is a documented-but-broken parameter.

A variable **category** is an editor-only organizational label, not persisted localizable game/UI text. UE itself stores it as plain `FString` metadata — `blueprint.set_variable_metadata` writes key `Category` via `FBlueprintEditorUtils::SetBlueprintVariableMetaData(..., ValueStr)` (`BlueprintPropertyHandler.cpp:540`), no FText path. The over-strict coercion was introduced by `F-require-ftext-localization-identity` (DONE), whose scope (line 24) swept "variable/function category settings" into the namespace+key net even though its own exclusion (line 26) and UE's metadata model treat categories as plain strings. Distinct from the WONTFIX `B-blueprint-set-variable-settings-transient-internal-error` (opaque, transient, retry-succeeds transport error) — this one is deterministic and reproducible every time.

**Workaround:** add the variable WITHOUT `category`, then set it via `blueprint.set_variable_metadata` (`variableName`, key `Category`, value `<category>`) — category-as-metadata is a plain string and bypasses the FText path. This is how the existing `ShowTutorOnlyOn1stLaunch` variable on the same BP carries its category.
**Fix:** for variable category specifically, build the FText with `FText::FromString(Category)` instead of `CoerceStringToPersistedFText` at `BlueprintPropertyHandler.cpp:151` and `:783` (and the parallel function-category path at `BlueprintFunctionHandler.cpp:952`); categories are not user-facing localized strings.

## History
- `#1-initial-repro` `OPEN` reporter — During edit of `/App/App/UI/LobbyAndMenu/HUD/W_HUD_PhotoInspection`: `blueprint.add_variable` args `{variableName:"TargetMarkerStyle", variableType:"struct:/Script/App.MinimapMarker", category:"Minimap", isPublic:true}` failed with `INVALID_TEXT_LOCALIZATION_IDENTITY`; `blueprint.set_variable_settings` `{variableName:"TargetMarkerStyle", category:"Minimap", isInstanceEditable:true, isPublic:true}` failed identically. Workaround verified: re-ran `add_variable` without `category` (success), then `blueprint.set_variable_metadata` `{variableName:"TargetMarkerStyle", key:"Category", value:"Minimap"}` (success); `property.get` confirmed the variable instance-editable under category Minimap. Root cause traced to `CoerceStringToPersistedFText` (`PropertyImport.cpp:201-238`) rejecting the plain string at handler sites `BlueprintPropertyHandler.cpp:151`, `:783`.
- `#2-additional-repro-pickup-bp` `OPEN` reporter — Additional evidence (independent repro on a fresh Actor BP `/Game/OracleReplay/BP_OracleReplayPickup`, seed `blueprint.add_variable`): `blueprint.add_variable {variableName:"HealthRestored", variableType:"int", defaultValue:"25", category:"Pickup", isPublic:true}` → `[INVALID_TEXT_LOCALIZATION_IDENTITY] Variable category requires an FText namespace and key: ... pass NSLOCTEXT("Namespace","Key","Source") ...`. Re-adding the same variable WITHOUT `category` succeeded; then `blueprint.set_variable_settings {variableName:"HealthRestored", category:"Pickup"}` failed with the identical error. Confirms deterministic reproduction on both handlers in UE 5.7 and that the failure aborts the whole `add_variable` (the variable is not created when `category` is rejected). Workaround found in the wild: pass `category` as `NSLOCTEXT("ns","key","Pickup")` (parser extracts the source string) — confirms the documented plain-`string` `category` param contract is broken on both methods.
- `#3-build-category-ftext-from-string` `IN-REVIEW` developer — Fixed at all three category sites by replacing `CoerceStringToPersistedFText(...)` with a direct `FText::FromString(Category)` (empty → `FText::GetEmpty()`), so a variable/function category is treated as the editor-only organizational label it is rather than persisted localizable text. Mirrors UE's own Variables/My-Blueprint panel category commit and existing in-repo precedent; the `CoerceStringToPersistedFText` gate stays intact for genuine persisted UI/game text (property/widget sets, BPIR pin defaults). Files: `Private/Handlers/Blueprint/BlueprintPropertyHandler.cpp` (`add_variable` ~:147, `set_variable_settings` ~:777; `NewVar.Category` assignment changed from `MoveTemp` to copy since the FText is now const), `Private/Handlers/Blueprint/BlueprintFunctionHandler.cpp` (`set_function_settings` category path ~:939, also dropping the now-unused `ExistingCategory`/`GetGraphFunctionMetaData` lookup). Reconciliation of `F-require-ftext-localization-identity` Scope line 24 (which deliberately swept variable/function categories in): categories are a distinct value class — UE stores them as plain `FString` metadata (`set_variable_metadata` "Category" key) — so carving them out is consistent with that gate's intent (localize user-facing text) while narrowing its literal scope; this is the same fix direction the FormatText precedent (`B-bpir-format-text-bare-string-roundtrip-break`) reasoned toward. Regression test: 3 new automation tests in `Private/Tests/Blueprint/TestBlueprintHandlers.cpp` (`blueprint.add_variable.PlainStringCategoryAccepted`, `blueprint.set_variable_settings.PlainStringCategoryAccepted`, `blueprint.set_function_settings.PlainStringCategoryAccepted`) drive the real registered handlers via the dispatcher with a plain-string `category` and assert success + that the stored category FText equals the input verbatim; reverting the fix restores the `INVALID_TEXT_LOCALIZATION_IDENTITY` SendError and fails them.
