# level.build_level_lighting job can stay running forever — completion delegate has no poll/watchdog fallback

`level.build_level_lighting` kicks off a per-level static-lighting (Lightmass) build as a job (`Ctx.StartJob`) and binds completion via `BindLightingBuildCompletion()`, which attaches first-fires-wins lambdas to `FEditorDelegates::OnLightingBuildSucceeded` / `OnLightingBuildFailed` / `OnLightingBuildKept`. Those delegates DO fire on a normal interactive completion (see "Engine source note" below), so the happy path works. The defect is that completion is reconciled by a **single in-memory one-shot delegate with no fallback**: there is no progress, no timeout, and no watchdog that reconciles against the engine's real build state. If the bound delegate is ever missed before its broadcast tick — an editor stall/recovery, an editor kill+relaunch (this fuzz host's clean-state policy kills the editor between iterations), GC/serialization deferral, or any non-CPU-Lightmass completion route that doesn't broadcast these three delegates — the job entry (purely in-memory in `FJobRegistry`, no persistence, no fallback poller) stays `{status:"running", progress:[]}` forever and never reaches a terminal state.

Repro (observed): on `/Game/Maps/Lighting/Lighting_Realtime` (UE 5.7, Content Examples host), `level.build_level_lighting {}` returned ticket `j_20260624T144900_2d631e32` `{status:"running"}`; the Lightmass bake then completed cleanly (editor log `LogStaticLightingSystem: ... storing lightmap data for 141 meshes`, `[957/957 mappings]`, `MapCheck: 0 Error(s)`), yet `system.job_status` still returned `{"status":"running","progress":[]}` 3h+ later. A control `level.save` job in the same session reached `completed` in 3s, so the job framework itself works.

**Engine source note (corrects the original #4 root-cause claim):** The earlier claim that "none of the three `FEditorDelegates` fire for the `FEditorBuildUtils::EditorBuild`/Lightmass path" is FALSE in UE 5.7. `FStaticLightingManager::SendBuildDoneNotification` broadcasts `OnLightingBuildSucceeded.Broadcast()` **unconditionally** (`StaticLightingSystem.cpp:290`); the `AutoApplyFailed` flag only sets the Slate notification's completion state (`:295`), it does NOT gate the broadcast. Both branches of the `AutoApplyingImport` stage (auto-apply `:2627` and wait-for-user `:2635`) call `SendBuildDoneNotification`, so the success delegate fires regardless of whether auto-apply is enabled. `ProcessLightingData` broadcasts `OnLightingBuildKept` (`:185`) and every failure path broadcasts `OnLightingBuildFailed` (`:201/:361/:437`). So the bug is NOT "the delegates never fire" — it is "there is no fallback when the one-shot in-memory delegate is missed." (The original #4 also prescribed polling `FEditorBuildUtils::GetBuildState()`, which does not exist in 5.7.)

**Fix:** Augment `BindLightingBuildCompletion()` with a poll-based watchdog (the same pattern `BindNavigationBuildCompletion` already uses), sharing the existing `bFired` first-fires-wins guard so the delegate still wins on the happy path. A `FTSTicker` watches `FEditorBuildUtils::IsBuildCurrentlyRunning()` (the real public 5.7 query — `EditorBuildUtils.h:213`); once it has seen the build start and then stop without any delegate having fired, it resolves the job to a terminal state. Do NOT remove the delegate binding and do NOT use the non-existent `GetBuildState()`. Same handler family (`level.build_lighting`, `lighting.build_lighting`, `level.build_all`) shares `BindLightingBuildCompletion()` and is fixed by the same change.

**Files:** `Plugins/PinWright/Source/PinWright/Private/Handlers/Level/LevelBuildBinds.h` (`BindLightingBuildCompletion`); call site `Handlers/Level/LevelHandler.cpp:1561` (`level.build_level_lighting`).
