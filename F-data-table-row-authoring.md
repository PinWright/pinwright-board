# DataTable row CRUD + struct rebind RPCs (live authoring surface)

`B-asset-dump-datatable-rows-missing` (DONE) added the read side: `asset.dump` on a `UDataTable` now emits a `data_table.json` sidecar via `Handlers/DataTable/DataTableDumpBuilder.{h,cpp}`, exposing `rowCount`, `rowStruct`, and an alphabetically-sorted `rows` map keyed by row name with each row's struct fields serialized through `FJsonObjectConverter::UStructToJsonObject`. There is no matching live authoring surface — grep across `Source/EditorAutomationRpcGateway/Private/Handlers/` finds zero RPC handlers that mutate a DataTable. The closest verbs (`property.set`, `object.call`) cannot edit `UDataTable::RowMap` safely because `RowMap` is a `TMap<FName, uint8*>` of struct allocations the table owns; writing through generic reflection bypasses the editor's `Modify` / `OnDataTableChanged` / asset-registry-tag refresh path and risks leaks or stale tag data.

This violates the dump-parity / authoring-parity policy followed by `F-rpc-blueprint-describe-struct` and `F-rpc-blueprint-class-properties`: anything the dump surfaces should be reachable and mutable via a live RPC, so authoring agents can write a row and verify it without a full `asset.dump` round-trip and without resorting to editor scripting hacks.

**Fix:** Add a `data_table` namespace with row CRUD + list + struct rebind verbs, all routed through `FDataTableEditorUtils` (which calls `Modify`, rebuilds `RowMap` correctly, fires `OnDataTableChanged`, and refreshes asset-registry tags) and `UDataTableFunctionLibrary` where it covers the case. Methods:

- `data_table.list_rows(assetPath)` — returns `{rowStruct, rowCount, rows:[{name, values}]}` mirroring the sidecar shape exactly so live and dumped views agree. Reuse `DataTableDumpBuilder`'s row-emission helper (lift it out of the builder's anonymous namespace into a public function the way `F-rpc-blueprint-describe-struct` lifted `BuildFieldJson`).
- `data_table.add_row(assetPath, rowName, values)` — `FDataTableEditorUtils::AddRow`; populate from `values` object via `FJsonObjectConverter::JsonObjectToUStruct` against `RowStruct`. Error if `rowName` already exists, if `RowStruct` is null, or if any required struct field is missing or type-mismatched (collect per-field errors into the response, do not partial-write).
- `data_table.set_row(assetPath, rowName, values, {createIfMissing=false})` — locate row via `RowMap`; copy `values` over the existing struct allocation using JSON→struct conversion. When `createIfMissing=true`, fall through to `AddRow` semantics. Always call `FDataTableEditorUtils::BroadcastPostChange(... RowDataChanged)` so listeners refresh.
- `data_table.remove_row(assetPath, rowName)` — `FDataTableEditorUtils::RemoveRow`. Error if row not present.
- `data_table.set_row_struct(assetPath, structPath)` — `UDataTableFunctionLibrary::SetRowStruct` if available; otherwise direct `UDataTable::CleanBeforeStructChange` / `RowStruct = NewStruct` / `OnPostDataImported` (the same path the editor's struct dropdown uses). This is destructive (all existing rows are dropped) — require an explicit `force=true` when `rowCount > 0`.

Implementation shape:
1. New directory `Source/EditorAutomationRpcGateway/Private/Handlers/DataTable/` already exists for the dump builder; co-locate handlers there as `DataTableAuthoringHandler.cpp` to keep all DataTable surface in one folder.
2. Each handler resolves the `UDataTable*` via `Ctx.RequireAssetPath()` + `LoadObject<UDataTable>` and bails with `ASSET_NOT_FOUND` / `NOT_A_DATATABLE` early; mutations go through `FDataTableEditorUtils` only (never raw `RowMap.Add` / `RowMap.Remove`) so editor invariants hold.
3. Wrap every mutation with `Table->Modify()` + `Table->MarkPackageDirty()`; do **not** auto-save (consistent with the plugin's other write verbs — saving is `system.save_asset`'s job).
4. Reuse the dump builder's struct→JSON row-emission code by exposing a public `DataTableDumpBuilder::BuildRowJson(const UDataTable*, FName)` helper; both `list_rows` and the return payloads of `add_row` / `set_row` use it so written-then-readback values are byte-identical to the dump.
5. Update `docs/wiki/asset.md` (which already mentions `data_table.json`) and add a new `docs/wiki/data_table.md` editorial overlay describing the namespace, the `force` rule on `set_row_struct`, and the parity with the dump sidecar.
6. Tests in `Source/EditorAutomationRpcGatewayTests/Private/DataTable/` (new folder) covering: add/set/remove on a non-empty fixture with the existing `FTestAssetDumpDataTableRow` struct, `set_row` with `createIfMissing` both ways, struct-change without `force` rejected when non-empty, struct-change with `force` succeeds and clears rows, error path on missing `rowName` / wrong struct shape.

**Out of scope (file a sibling ticket):** CSV/JSON bulk import via `UDataTableFunctionLibrary::FillDataTableFromCSVString` / `FillDataTableFromJSONString` and export verbs. Bulk import has separate concerns (replace-vs-merge mode, per-row error reporting, struct-binding for fresh tables) that warrant their own ticket once the CRUD surface lands and proves the wiring.
