# `blueprint.graph.*` GRAPH_NOT_FOUND doesn't enumerate graphs or hint that an event name isn't a graph

`blueprint.decompile` presents each event body as `entry override Tick(...)`, `entry custom_event Foo(...)`, etc. A caller naturally passes that name as `graphName` to a follow-up `blueprint.graph.*` call, but events live inside the shared `EventGraph` ubergraph, so `graphName:"Tick"` fails with `GRAPH_NOT_FOUND: Could not find graph 'Tick' in blueprint.` The error lists no valid graph names and gives no hint that `Tick` is an event inside `EventGraph`.

The explicit-`graphName` path of `blueprint.graph.find_nodes` (`BlueprintGraphInspectionHandler.cpp:855-858`) delegates resolution to the shared `ResolveBlueprintAndGraph` (`BlueprintGraphHelpers.cpp` resolver), which matches `graphName` only against `UEdGraph::GetName()` over function/ubergraph/`GetAllGraphs()` — that is EventGraph / function / macro / delegate graph names, never event/entry names — and on no match emits the bare `GRAPH_NOT_FOUND` (resolver error site, formerly `BlueprintGraphHelpers.cpp:88-92`) with no available-graph list and no event hint. The same shared resolver backs every other `blueprint.graph.*` mutator, so they all inherit this. `blueprint.references` (`BlueprintGraphHandler.cpp`) has its own near-identical bare `GRAPH_NOT_FOUND` (formerly lines `91-92`). (The ticket originally miscited `find_nodes` to `BlueprintGraphHandler.cpp:79-95`; that is the `blueprint.references` handler, not `find_nodes`.)

Distinct from `E-find-nodes-eventgraph-default` (which made an *omitted* `graphName` search all graphs — that fix is intact, and it deliberately left `ResolveBlueprintAndGraph` unchanged); this is about an *explicit* `graphName` that is an event name being rejected with an unhelpful message.

**Workaround:** Omit `graphName` (now searches all graphs after `E-find-nodes-eventgraph-default`), or pass `"EventGraph"` — events live in the ubergraph.
**Fix:** Make the shared `GRAPH_NOT_FOUND` error enumerate the blueprint's available graph names and hint that the name may be an event inside `EventGraph` (events are nodes, not graphs of their own). Scoped to the message at the two error sites — the resolver and `blueprint.references` — via a shared `BlueprintGraphHelpers::BuildGraphNotFoundMessage`. Deliberately does **not** add event-name→ubergraph alias resolution: that would change load-bearing `graphName` semantics across ~20 shared callers and mask the EventGraph distinction — out of scope for this Low-severity ergonomic message fix.
