# BPIR `select` loses literal FText options

Reproduced live, UE 5.8, plugin `d195a55d`, on a scratch Actor Blueprint:

```
%t = select(cond: $bFlag,
            true:  "NSLOCTEXT(\"PwTest\",\"Yes\",\"YES\")",
            false: "NSLOCTEXT(\"PwTest\",\"No\",\"NO\")")
-> compiled: true, errors: []
```

`get_pin_details` on the Select node's `Option 0`:

```json
{"pinName":"Option 0","direction":"Input","pinType":"text",
 "defaultValue":"NSLOCTEXT(\"PwTest\",\"No\",\"NO\")"}
```

The pin is typed `text`, the literal sits in **`defaultValue`** as a raw string, and there is **no
`defaultTextValue` field**. `get_pin_details` emits that field only when non-empty
(`BlueprintGraphCrudHandler.cpp:2230-2232`), so its absence is the failure signal. At runtime the
option compiles to empty `FText` — presenting as "one branch of the field is blank".

**Control, same asset, same literal, same compiler** — a function input pin:

```json
{"pinName":"InText","direction":"Input","pinType":"text","defaultTextValue":"DIRECT"}
```

Correct slot, no raw `defaultValue`. The difference is the pin, not FText handling.

## Mechanism

PinWright's text path is correct and is what makes the function-input case work —
`Compiler/CodePinResolver.cpp:72-90` writes `Pin->DefaultTextValue` and clears `DefaultValue` when the
pin is already `PC_Text`.

It is never reached for Select options. `UK2Node_Select` allocates every option pin as `PC_Wildcard`
(`Editor/BlueprintGraph/Private/K2Node_Select.cpp:232/238/260`), and the node is created that way by
`Compiler/CodeNodeEmitter.cpp:813-828`. So the literal falls through to the wildcard escape hatch at
`CodePinResolver.cpp:233-236`, which writes `DefaultValue` only — with a comment saying it exists so
values "persist for round-trip".

The ordering makes it unavoidable: `BpirCompiler.cpp:3124-3135` (pass 3a) applies option literals at
the Select's own instruction index, while the Return Value is typed only when a later instruction
consumes `%ref`. Type resolution always arrives after the literal.

When the type does arrive, `UK2Node_Select::OnPinTypeChanged` (`K2Node_Select.cpp:869-883`) re-types the
option pins and calls `ResetPinToAutogeneratedDefaultValue` for any whose default is now invalid —
leaving `PC_Text` with an empty `DefaultTextValue` and a stray string in `DefaultValue`.

## Why the round-trip looks clean

`blueprint.decompile` prints the `DefaultValue` string back verbatim, so a decompile-diff shows the
`NSLOCTEXT(...)` literals present and the round-trip appears lossless. Verified live — the decompile
output was byte-correct while the pin was already broken.

## Related, same root cause

A **literal** on the Select's index pin fails the same way, loudly. Observed live:

```
select(cond: true, ...)  ->  BLUEPRINT_COMPILE_FAILED
  "The type of Index is undetermined. Connect something to Select to imply a specific type."
```

The documented example (`wiki-src/bpir.instructions.md:168`) uses a **variable** (`$bIsDay`), which types
the pin. A literal boolean does not. Worth covering in the same fix.

## Fix lever, already parsed and unused

`%n1: text = select(...)` is parsed into `FBpirInstruction::DeclaredResultType` / `bHasDeclaredResultType`
(`BpirTypes.h:137-138`, set at `BpirParser.cpp:1690-1691`) and the compiler never reads it — its only
other references are parser unit tests. Pre-typing the Select's Return Value from the declared result
type (or from the literal's shape) before applying option defaults would fix both the FText loss and the
undetermined-int error.

## Coverage gap

`Tests/Compiler/TestCompilerMacrosEntryPoints.cpp:226-248` uses **String** literals consumed by a
`PC_String` pin — the one literal kind whose wildcard `DefaultValue` write happens to survive re-typing —
and asserts only `bSuccess` plus a node count. No FText select-option case, no int select-option case, no
assertion on any option pin's default. `Docs/bpir-test-matrix.md:59` marks `select` coverage "Full",
which is how this survived.

## History

- `#1-reported-with-live-repro` `OPEN` reporter — Confirmed at runtime on `d195a55d` / UE 5.8: Select `Option 0` typed `text` carrying the raw literal in `defaultValue` with `defaultTextValue` absent, against a same-asset function-input control showing `defaultTextValue:"DIRECT"`. Decompile round-tripped the literals cleanly while the pin was broken. Literal index-pin variant reproduced as the documented "undetermined" compile error.
- `#2-pretype-select-option-pins` `IN-REVIEW` developer — Fixed by pre-typing the Select's Return Value and option pins at emit time, before pass 3a applies option literals, so `FCodePinResolver::SetPinDefaultValue` takes its `PC_Text` branch and writes `DefaultTextValue` instead of the wildcard escape hatch's `DefaultValue`. Two type sources in `Compiler/BpirCompiler.cpp` (new statics `ResolveSelectResultPinType` / `PreTypeSelectPins`, called from the `EBpirOpcode::Select` emit case): the previously-unused `FBpirInstruction::DeclaredResultType` (which `BpirTextEmitter::ResolvePrimaryOutputTypeAnnotation` already emits for every select, so decompile/recompile now restores the type), and an option literal that `CoerceStringToPersistedFText` accepts as an FText with a real localization identity. Bare quoted strings have no identity and are untouched, so string selects behave exactly as before. Pin types are stamped directly rather than via `UK2Node_Select::ChangePinType`/`OnPinTypeChanged`, avoiding the `bReconstructNode` side effect that would invalidate the pin pointers the emit pass just cached; option pins are found by walking `Pins` because `GetOptionPins()` keys off `IndexPinType`, which `SetEnum` leaves at its `PC_Wildcard` default on a freshly emitted enum-backed select. Files: `Source/PinWright/Private/Compiler/BpirCompiler.cpp` (+ `Utils/PropertyImport.h` include), `docs/bpir-test-matrix.md`. Test added: `PinWright.bpir.round_trip.SelectTextOptionLiteral` (`Source/PinWright/Private/Tests/Bpir/TestBpirSelectTextOptionLiteral.cpp`) — asserts each option pin is `PC_Text`, carries a non-empty `DefaultTextValue` with the original display string and key, and has an empty `DefaultValue`; then decompiles, asserts the `NSLOCTEXT` identity and the `: text = select(` annotation survive, and recompiles the decompiled source into a fresh BP asserting the same pin state (that leg covers the declared-result-type path). NOT fixed here and reported separately: the literal-index variant (`select(Index: <literal>)` leaves the Index pin `PC_Wildcard`) — logged as gap 23 in `docs/bpir-test-matrix.md`; and `make_array`, whose element pins are wildcard on the same code path and lose FText literals identically.
