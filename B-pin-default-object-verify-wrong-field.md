# `blueprint.graph.set_pin_default_value(s)` reports VERIFICATION_FAILED for object-reference pins it actually set

Setting an object-reference input pin's default (e.g. `TObjectPtr<UTexture2D>`) via `set_pin_default_values` (and the singular `set_pin_default_value` — both route through `ApplyPinDefaultValueCore`) succeeds in writing the pin's `DefaultObject`, but the handler's post-write verification only inspects the string `Pin->DefaultValue` (and `Pin->DefaultTextValue`). For object/class/softobject/interface pins the value lives in `Pin->DefaultObject`, leaving `DefaultValue` empty. So `bMatchesRequested` is false and `bNoStateChange` is true, and the call returns `success:false, error:"VERIFICATION_FAILED", message:"... but pin remained ''"` even though the edit is correct. Callers see a false failure and may retry or take corrective action against already-correct state.

In `BlueprintGraphCrudHandler.cpp` the `else` (non-enum, non-PC_Text) branch of `ApplyPinDefaultValueCore` (lines 2158-2176) calls `Schema->TrySetDefaultValue` then verifies via `Pin->DefaultValue.Equals(Value)` / `Pin->DefaultTextValue` only — it never reads `Pin->DefaultObject`. Object-category pins (`PC_Object`, `PC_Class`, `PC_SoftObject`, `PC_SoftClass`, `PC_Interface`) keep `DefaultValue` empty, so verification always fails for them.

**Workaround:** Ignore the `VERIFICATION_FAILED` result for object-pin sets; confirm with `blueprint.graph.get_node_details` (reports `defaultObjectPath`), then `blueprint.compile`/save.
**Fix:** In the verify branch, detect object-category pins (`PC_Object`/`PC_Class`/`PC_SoftObject`/`PC_SoftClass`/`PC_Interface`) and compare the resolved `Pin->DefaultObject` (or its path) against the requested path instead of `Pin->DefaultValue`.
