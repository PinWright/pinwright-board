# compile_bpir upsert that fails placement validation deletes the pre-existing event graph

`blueprint.compile_bpir` defaults to upsert (`append`/`replace`) mode, where Phase 0 deletes the matching existing entry node + its exec-reachable subgraph **before** the new BPIR is emitted. The authored-position placement validation (`@(x, y)` all-or-none, and the zero-node `@(x,y)` marker reject) runs **after** emission — i.e. after that Phase 0 delete. When an upsert of an existing event fails this placement validation, the compile returns `COMPILE_FAILED`, but the failed-compile rollback only removes nodes **created** during the compile; it never re-adds the Phase-0-deleted entry, and the caller's scoped-transaction undo restores the deleted node objects without their entry→body exec links. The result is a silently gutted event graph (entry stripped, body orphaned) that then compiles `UpToDate` with no integrity trip and is persisted to disk by `asset.save`. Replay-confirmed three times this session (history #10/#11/#12) across two distinct placement triggers (mixed authored-position, zero-node `@(x,y)` marker).

The original #1 symptom (a `UTransBuffer::IsObjectTransacting` ensure + transport hang on the rollback path) is a **separate, already-fixed** concern — see #6/#8 (Apply+Cancel transport fix) verified DONE in #7/#9. This ticket now tracks only the live silent-data-loss regression above.

**Fix:** Validate authored-position placement mode **before** the Phase 0 delete (and before the scoped transaction), so a placement-mode violation fails the compile while the pre-existing graph is still untouched — instead of after Phase 0 has destroyed it and left the rollback unable to restore its exec links.

**Workaround:** Avoid re-upserting an existing event with a partially-positioned body; use read-only BPIR decompile/asset dump for investigation, then apply surgical `blueprint.graph` edits. This is not a global blocker for Blueprint-only edits.
